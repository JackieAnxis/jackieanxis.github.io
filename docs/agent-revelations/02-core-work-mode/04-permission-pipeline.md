# 权限管线：Agent 的护栏

上一节讲了工具系统——Agent 的双手。Agent 在一次会话中可能调用几十次工具，每次调用都潜藏风险：一个 `rm -rf`，一次意外的 `npm publish`，都可能造成不可逆的后果。

权限管线（Permission Pipeline）正是为 Agent 构建的安全护栏。它不是简单的"允许/拒绝"开关，而是一条多阶段检查管线。
每一层独立运作，即使某一层被绕过，下一层仍能拦截。这就是"纵深防御"：在自动化效率与安全控制之间寻找精确的平衡。

## 四大关卡：权限检查的四阶段管线

每次工具调用都需通过四个阶段，任何阶段做出终局决定后，后续阶段跳过。

1. **入口安检——格式验证**：检查工具参数是否完整、格式是否正确。参数不合法则拒绝，但系统不会直接崩溃，而是降级为用户确认。

2. **通行证检查——规则匹配**：系统维护三份名单，按顺序依次检查：

    ```text
    deny：在拒绝名单上      -> 立即拒绝，后续不再检查
    ask：被标记为"总是询问" -> 强制弹出确认
    allow：在放行名单上     -> 直接通过
    ```

    **铁律**：优先级为 `deny` > `ask` > `allow`，无论规则来自全局配置、项目配置还是命令行参数，**只要有一个地方配置了高优先级的，就会覆盖其他地方的配置**。

3. **场景评估——上下文评估**：前两关是通用的，本关由每个工具自行实现精细检查。工具返回四种判断：
    | 判断 | 含义 |
    |------|------|
    | `allow` | 放行 |
    | `deny` | 拒绝 |
    | `ask` | 要求人类确认，后续 allow 规则无法覆盖 |
    | `passthrough` | 无意见，交给后续关卡，可被 allow 规则覆盖 |

    `passthrough` 与 `ask` 的区别：前者是"我不管，后续决定"，可被 allow 覆盖；后者是"我要求人类确认"，不可被 allow 覆盖。

    以 Bash 工具收到 `rm -rf /tmp/test` 为例：它会解析出子命令是 `rm`，检查目标路径，然后匹配用户配置的规则——如果用户之前 allow 过 `Bash(rm:*)`，返回 `allow`；如果没有匹配到任何规则，返回 `passthrough`。

4. **人工窗口——交互确认**：前三关均未终局时，系统弹出交互提示。但"人工窗口"里的决策者不止一个——实际上有三个角色在竞争做决定。

    - **Hook 脚本**——系统管理员编写的自动审批逻辑，信任等级最高。比如 CI/CD 环境中，Hook 脚本可根据自定义规则自动批准或拒绝。
    - **用户**——终端界面手动选择"允许/拒绝/本次允许"，可将决策持久化到配置文件。
    - **AI 分类器**——auto 模式下，另一个 AI 模型判断当前操作是否安全（"AI 监督 AI"），信任等级最低。后文会详细展开它的工作方式（auto 模式疑似只针对 Anthropic 内部员工开放）。

    三者可能同时响应，但是权限请求只能被一个决策者认领，先到先得。

    部分安全检查是**分类器免疫**的——涉及 `.git/`、`.claude/` 等核心目录的操作，无论分类器如何判断，必须人工确认。


## 五种权限模式

权限模式控制"关卡有多严格"，从严格到宽松排列：

### default：逐次确认

每次工具调用都需用户确认（被 allow 规则放行的除外）。最安全也最繁琐。

### plan：只读模式

写入和命令执行被拒绝，只读操作放行。适用于代码审查和架构分析——先理解再行动。

### auto：AI 分类器

注：auto 模式疑似只针对 Anthropic 内部员工开放。

用另一个 AI 模型代替人工审批——"AI 监督 AI"。每次分类器调用都是一次 API 请求，有延迟、有成本，所以系统按顺序做了几层处理：

**第一层：白名单快速通道。** 约 20 个被标记为"安全"的工具（读文件、搜索代码、管理任务列表等）直接跳过分类器检查，不浪费 API 调用。

**第二层：分类器两阶段判断。** 没被白名单跳过的操作，交给分类器。分类器收到三样东西：
- **对话历史的压缩摘要**（只包含用户的原始输入和 Agent 的工具调用，不包含 Agent 自己生成的文字——防止 Agent 用自己的输出来"说服"分类器）
- **当前要执行的操作**
- **用户的 allow/deny 规则和 CLAUDE.md 配置**

分类器本身分两步走：

1. **快速阶段**：先让模型给出一个即时的"放行/阻止"，只分配极少 token（64 个）。如果快速阶段说"放行"，直接通过。
2. **深度阶段**：快速阶段说"阻止"时才触发。给模型更多 token（4096 个）展开思考，减少误判——快速阶段倾向于"宁可错杀"，深度阶段给模型机会重新审视。

**第三层：熔断兜底。** 如果分类器连续 3 次拒绝，或本次会话累计拒绝 20 次，系统自动回退到人工确认——就像保险丝，当自动决策连续失败时，切断自动审批，回到人类把关。

贯穿全程的安全底线：核心安全目录（`.git/`、`.claude/` 等）的操作是**分类器免疫**的，分类器无权批准，必须人工确认。

### bypassPermissions：绕过权限

几乎全部放行，但以下防线仍生效：deny 规则、需用户交互的特殊检查、不可绕过的安全检查（如修改 `.git/config`）。适用于 CI/CD 和受控环境。

### bubble：子代理权限冒泡

内部模式，不对外暴露。子代理的权限检查冒泡回主代理上下文，权限绝不超过父级。


## 规则如何生效和记住：权限更新的两层机制

用户在权限提示中有两种选择：

- **"仅允许一次"**——规则只写入内存，本次会话有效，关闭后消失。
- **"始终允许"**——规则写入内存（立即生效）的同时，也写入配置文件（持久化），重启后仍然有效。

两者的共同点是内存即时生效，区别只在是否持久化到文件。持久化失败不影响当前会话——"现在能正常用"比"将来一定能记住"更紧急。

### 规则来源与优先级

从低到高：

| 来源 | 作用范围 |
|------|---------|
| 全局用户设置 | 本机所有项目 |
| 项目设置 | 提交到版本控制，团队共享 |
| 本地设置 | 不提交版本控制，仅自己，"始终允许"的规则写在这里 |
| 命令行参数 | 本次启动时临时指定 |
| 会话级规则 | 本次会话，"仅允许一次"的规则写在这里 |

高优先级覆盖低优先级。

### 配置建议

- **团队共享**：项目设置（`.claude/settings.json`，提交版本控制）
- **个人偏好**：本地设置（`.claude/settings.local.json`，不提交）
- **临时需求**："仅允许一次"（会话级规则，不污染任何配置文件）
