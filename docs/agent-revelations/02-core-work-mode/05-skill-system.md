# 技能系统：Agent 的训练手册

如果说 Agent Loop 是 Agent 的心跳，工具系统是它的双手，那技能系统就是一本**训练手册**。

有了手，Agent 能读写文件、执行命令。但"能做什么"不等于"知道怎么做"。面对一个新项目，Agent 不知道你们的 Git 提交规范、不知道代码审查要检查哪些项、不知道部署流程分几步。这些领域知识不能靠模型自己猜——它们需要被注入。

最直接的办法是把所有知识都塞进系统提示。但 10 个技能，每个 2000 token，就是 20000 token 的上下文消耗，大部分跟当前任务毫无关系。

技能系统的解法是**两阶段注入**：

```
第一阶段：系统提示（始终在场，低成本）
+--------------------------------------+
| Skills available:                    |
| - git-workflow: Git 工作流规范       |  ~100 tokens/skill
| - code-review: 代码审查清单          |
| - deploy: 部署流程指南               |
+--------------------------------------+

第二阶段：按需加载（用到才给，高价值）
+--------------------------------------+
| 完整的技能内容...                    |  ~2000 tokens/skill
| 步骤 1：检查分支命名规范             |
| 步骤 2：验证 commit message 格式     |
| ...                                  |
+--------------------------------------+
```

系统提示只放名称和一行描述，模型需要时才加载完整内容。用到什么知识，临时注入什么知识。


## 五层技能来源：谁说了算

技能不是从一个地方来的。Claude Code 的技能来自五个层级，每层有不同的管辖范围和优先级：

| 层级 | 存放位置 | 谁管理 | 作用范围 |
|------|---------|--------|---------|
| 管理策略级 | 集中配置路径 | 企业管理员 | 全公司统一标准 |
| 用户级 | `~/.claude/skills/` | 个人开发者 | 跨所有项目的个人偏好 |
| 项目级 | `.claude/skills/` | 项目团队 | 仅当前项目生效 |
| 插件级 | 插件目录 | 插件开发者 | 插件自带的能力 |
| 内置级 | 编译进二进制 | Claude Code 团队 | 开箱即用的核心技能 |

高优先级来源可以覆盖低优先级的同名技能。比如企业管理员下发的代码审查规范，优先级高于开发者个人的审查习惯。去重时系统会用 `realpath` 解析符号链接，避免同一个技能通过不同路径被加载两次。

这像一个公司的制度层级：总公司政策 > 分公司规范 > 部门规章 > 外部合作方建议 > 行业通用常识。高层级的规范可以覆盖低层级，但每个人仍然可以保留自己的工作习惯——只要不跟公司政策冲突。

值得注意的是，管理策略级可以被环境变量禁用。这保留了开发者的自主权：在自己的机器上，你可以选择不执行公司的强制技能。


## 技能怎么加载：从注册到激活

技能的加载分三个阶段，从静态到动态，逐步扩展 Agent 的知识范围。

**静态加载——入职培训。** 启动时，系统并行扫描五个来源目录，合并去重后得到完整的技能列表。内置技能在编译时就已经注册，不需要文件系统读取。旧版 `commands/` 目录也仍然兼容，只是标记为已弃用。

**动态发现——按需学习。** 有些技能不在启动目录里，而是藏在项目深处。当模型操作文件（读取、写入、编辑）时，系统会沿文件路径向上查找 `.claude/skills/` 目录。

典型的场景是 Monorepo。每个子项目可以有自己独立的技能：

```
my-monorepo/
├── packages/
│   ├── frontend/.claude/skills/component-gen/SKILL.md
│   ├── backend/.claude/skills/api-gen/SKILL.md
│   └── shared/.claude/skills/type-gen/SKILL.md
```

当模型操作 `packages/frontend/` 下的文件时，自动发现前端的组件生成技能；操作 `packages/backend/` 时，自动发现 API 生成技能。按位置激活，无需手动配置。

动态发现有一个安全过滤：被 `.gitignore` 忽略的目录自动跳过。这防止了 `node_modules` 中的恶意技能被静默加载。

**条件技能——触发式记忆。** 有些技能带了 `paths` 字段（比如 `paths: ["src/**/*.ts"]`），它们不会立即可用，而是进入"待命"状态。只有当模型操作的文件路径匹配 `paths` 模式时，技能才被激活。

条件技能一旦激活就永久有效——即使后续操作的文件不再匹配，技能也不会消失。这是为了防止模型正在基于某个技能执行任务时，技能突然"蒸发"导致行为不一致。

三个阶段串联起来：启动时学一遍基础知识（静态加载），工作中学到新知识（动态发现），特定场景唤醒专门知识（条件技能）。


## 技能怎么执行：翻开手册那一刻

技能被激活后，模型通过 Skill 工具调用它。执行方式有两种：

**Inline 模式（默认）。** 技能内容直接注入当前对话，共享上下文和 token 预算。就像在工位上翻开手册边看边做——适合轻量级任务，比如代码审查、格式化、项目规范查询。

**Fork 模式。** 技能在独立子代理中运行，拥有独立的上下文和 token 预算。就像把手册带到独立办公室，关上门专心处理——适合长时间运行的任务，比如批量重构、复杂代码生成。

用户调用技能时可以传入参数。比如 `/code-review src/api/auth.ts`，技能内部通过参数替换获取文件路径：

- `$ARGUMENTS` → 完整参数字符串 `src/api/auth.ts`
- `$1`, `$2` → 位置参数（`$1` = `src/api/auth.ts`）
- 命名参数 → 如果 frontmatter 定义了 `arguments: file_path`，则 `$file_path` = `src/api/auth.ts`

替换按顺序执行：先替换命名参数，再替换位置参数，再替换完整参数。如果技能内容里没有任何 `$` 占位符，参数会追加到内容末尾。

技能还可以限定允许使用的工具列表（`allowed-tools`）。一个只做代码审查的技能，只需要读取和搜索工具，不需要写入和执行权限——这是最小权限原则的体现。只包含只读工具的技能会自动放行，无需用户额外确认。


## 安全边界：不是什么手册都能信任

技能来自不同信任等级的来源，安全策略随信任等级递减：

**内置 > 管理策略 > 用户/项目/插件 > MCP（外部服务）**

为什么 MCP 的信任等级最低？因为 MCP 技能来自外部服务器。如果允许 MCP 技能中的 Shell 命令内联执行，一个恶意服务器可以注入 `rm -rf /` 这样的危险操作。本地技能（用户自己创建）则不受此限制——信任边界区分了"自己写的"和"别人给的"。

内置技能也有自己的安全设计。某些技能附带参考文件，首次调用时需要从二进制中提取到磁盘。提取过程使用 `O_NOFOLLOW + O_EXCL` 标志——前者防止符号链接劫持，后者确保是新建文件而非覆盖已有文件。就像从保险柜取出文件时，先确认抽屉没有被掉包。

动态发现的安全过滤在加载阶段已经提到：`.gitignore` 目录自动跳过。但安全不是只靠一道防线——即使恶意技能通过了动态发现，执行阶段的权限管线（上一节的内容）仍会拦截危险操作。

这就像公司对待不同来源的文档：总部发的制度无条件执行，外部合作方提交的流程文档需要安全审查后才能采纳。每一层都有独立的防线，任何一层拦截即可阻止风险。


## 写一本自己的训练手册

技能的基本格式很简单：一个目录加一个 `SKILL.md` 文件。

```markdown
<!-- ~/.claude/skills/code-review/SKILL.md -->
---
description: 执行代码审查，关注安全性、性能和可维护性
when_to_use: 当需要审查代码变更时使用
arguments: file_path
allowed-tools:
  - Read
  - Grep
  - Glob
---

对文件 $file_path 进行全面代码审查。

检查以下方面：
1. 安全漏洞（注入、敏感数据泄露）
2. 性能问题（不必要的循环、内存泄漏风险）
3. 可维护性（命名、复杂度、重复代码）
4. 错误处理的完整性

输出结构化的审查报告，按严重程度分级。
```

### 三条核心原则

**一个技能只做一件事。** 技能越大，模型执行的不确定性越高。如果发现技能内容超过 200 行，考虑拆分。"全栈开发"技能不如"API 生成"、"组件生成"、"测试生成"三个独立技能好使。

**描述要精确。** `description` 是模型选择技能的依据——模糊的描述会导致模型在不该用的时候用了，该用的时候没选对。"代码审查"比"帮助开发者改进代码"好得多。

**用条件技能减少噪音。** 给技能加上 `paths` 字段，只在操作匹配文件时才激活。项目里有 20 个技能不是问题，但如果 20 个技能全部同时出现在技能列表里，模型的选择质量会下降。条件技能让"用得到的技能"自动浮出水面。

### 反模式

- **不要创建"万能技能"**：一个技能包罗万象，看起来强大，实际执行质量很低。小而专注的技能更容易调试、更容易复用。
- **不要把敏感信息写在技能里**：技能内容会被发送给模型，不要包含 API 密钥、密码等。需要密钥的操作，让技能通过环境变量引用，而不是明文写入。
