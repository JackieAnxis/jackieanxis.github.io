# 计划与任务系统：Agent 的行动蓝图

如果 Agent Loop 是心跳，工具系统是双手，技能系统是训练手册，那计划与任务系统就是 Agent 的**行动蓝图**和**项目看板**。

有了手和技能，Agent 能读写文件、能执行代码、知道项目规范。但面对一个复杂任务——"把这个库从 React 17 迁移到 18"——它不会一句"好的我来做"然后凭记忆做到哪算哪。它需要先出方案、列工序、排工期、盯进度。

普通聊天机器人的对话是线性的：一问一答，聊完就散。但现实中的任务是并行的、有依赖的、会回滚的。计划与任务系统，正是在这两者之间架桥。


## 为什么 Agent 需要计划

一个复杂任务包含多个步骤，这些步骤之间往往存在依赖关系。比如迁移 React 版本：

```text
任务：将项目从 React 17 升级到 18

步骤 1：升级 package.json 中的 React 版本    ← 可以做
步骤 2：修复被废弃的 API 调用                ← 依赖步骤 1
步骤 3：更新依赖库到兼容版本                 ← 依赖步骤 1
步骤 4：替换 Concurrent Mode 相关代码        ← 依赖步骤 2、3
步骤 5：全量回归测试                         ← 依赖步骤 4
```

如果没有计划系统，Agent 只能靠上下文记忆来推进。但上下文会被压缩、会被截断、会被无关信息干扰。计划系统把"我记得要做到第几步了"变成一张显式的、不会丢失的清单。

计划系统解决四个核心问题：

| 问题 | 没有计划 | 有计划 |
|------|---------|--------|
| 拆解 | 大目标模糊，容易遗漏子步骤 | 每步都是可执行的小任务 |
| 排序 | 依赖关系隐式存在，容易搞错顺序 | 依赖显式声明，顺序一目了然 |
| 追踪 | "做到哪了"需要翻对话历史 | 任务看板实时反映进度 |
| 验证 | 做完了但可能方向错了 | 每步完成后对照原始目标检查 |

这就像装修工程——你可以对工人说"帮我装修"，但工人需要先量房、出方案、排工序，而不是拿着锤子直接砸墙。


## 计划的制定：纸上谈兵

面对复杂任务，Agent 的第一步不是修改代码，而是进入**计划模式**（Plan Mode）。

Plan Mode 的核心约束是**只读不写**——Agent 可以搜索代码、阅读文件、理解架构，但不能执行任何修改。这像一个医生先开诊断方案，病人确认后再开药：先理解，再行动。

```text
用户提出复杂任务
       │
       ▼
┌─────────────────────┐
│   Plan Mode（只读）  │
│                     │
│  搜索代码           │
│  理解架构           │
│  设计方案           │
│  列出实现步骤       │
│  标注依赖关系       │
└─────────┬───────────┘
          │
          ▼
    人类审查计划
    ┌───┴───┐
    │       │
   通过    修改
    │       │
    ▼       │
┌───────────────┐
│   执行阶段     │
│   （读+写）    │
└───────────────┘
```

Plan Mode 解决了两个关键问题：

**方向性错误的代价。** 如果 Agent 没理解清楚就直接动手，可能改了 20 个文件后发现方向错了。撤销 20 个文件的改动比撤销 0 个文件贵 20 倍。Plan Mode 把"理解"和"行动"分离，在零成本阶段确认方向。

**计划的产出是什么？** 一份任务列表——每个任务标注做什么、为什么做、有什么前置条件。这份任务列表就是计划的载体，也是下一节的内容。


## 任务的载体：任务管理工具

计划不能悬浮在空中，需要一个载体来承载。任务系统提供了一套工具，让 Agent 能在当前会话中显式地管理计划中的每一步。

### 创建任务：从计划步骤到显式工单

计划中的每个步骤被创建为一张"任务卡片"，标注：
- **做什么**（subject）：简短的任务标题
- **为什么做**（description）：背景、要求、注意事项
- **前置条件**（blockedBy）：哪些任务必须先完成

```text
任务看板：升级 React 17 → 18
┌────┬──────────────────────────────────┬───────────┬──────────┐
│ ID │ 任务                              │ 状态       │ 依赖     │
├────┼──────────────────────────────────┼───────────┼──────────┤
│ 1  │ 升级 package.json 中的 React 版本 │ completed  │ 无       │
│ 2  │ 修复被废弃的 API 调用            │ in_progress│ 依赖 1   │
│ 3  │ 更新依赖库到兼容版本              │ pending    │ 依赖 1   │
│ 4  │ 替换 Concurrent Mode 相关代码    │ pending    │ 依赖 2,3 │
│ 5  │ 全量回归测试                      │ pending    │ 依赖 4   │
└────┴──────────────────────────────────┴───────────┴──────────┘
```

### 状态流转：任务的生命周期

每个任务有清晰的状态生命周期：

```text
pending ──→ in_progress ──→ completed
   ↑                              │
   │         验证失败              │
   └──────────────────────────────┘
```

- **pending**：计划中但尚未开始
- **in_progress**：正在执行
- **completed**：已完成，通过验证

关键设计：**标记完成**和**开始下一件**是两个独立动作。Agent 不能"顺手"把两个步骤合并——这防止了"以为做完了其实没做完"的疏漏。

### 依赖管理：谁先谁后

任务之间的依赖通过 `blocks` 和 `blockedBy` 显式声明：
- 任务 1 `blocks` 任务 2 = 任务 2 `blockedBy` 任务 1
- 任务 4 依赖任务 2 和 3 = 任务 2 和 3 都完成后，任务 4 才可执行

依赖关系不是装饰——它是 Agent 执行时的硬性约束。被依赖的任务未完成时，Agent 不会"忘记"这个限制去执行后续任务。

### 进度看板：不会丢失的记忆

任务列表就像一张项目看板。对人类来说，这是透明度——随时能看到"做了多少、还剩多少"。对 Agent 来说，这是**防遗漏的安全网**——上下文被压缩时，任务列表告诉 Agent "我已经做了哪些事，接下来该做什么"。


## 从计划到执行：Agent 的工作循环

有了计划，Agent 怎么一步步落地？一个典型的长任务执行循环如下：

```text
┌──────────────────────────────────────────┐
│                                          │
│  ① 查看看板    还有哪些 pending 任务？    │
│     │         哪些依赖已解决？            │
│     ▼                                    │
│  ② 领取任务    选择一个可做任务，         │
│     │         标记为 in_progress          │
│     ▼                                    │
│  ③ 执行        调用工具完成它             │
│     │         （读、写、运行、搜索）       │
│     ▼                                    │
│  ④ 标记完成    确认成果，标记 completed   │
│     │                                    │
│     ▼                                    │
│  ⑤ 回到 ①     直到所有任务完成            │
│                                          │
└──────────────────────────────────────────┘
```

这个循环看起来简单，但有几个关键设计决策值得展开。

### 为什么不直接做，而是先创建任务？

因为**先列清单再勾选**比**凭记忆做到哪算哪**可靠得多。创建任务本身就是一次"我接下来要做什么"的显式思考。这能大幅降低 Agent 遗漏步骤的概率——尤其是当任务有 10 个以上子步骤时。

### 只有一个 Agent 也要用任务系统吗？

是的。即使只有一个 Agent 在工作，任务系统仍然提供了两个不可替代的价值：

**进度锚点。** 上下文窗口有限，当对话变长时，早期内容会被压缩或摘要。任务列表是压缩过程中保留下来的"骨架"——Agent 不需要回忆"我之前做到哪了"，看任务列表就知道。

**人类透明度。** 用户不用翻 50 轮对话来了解进度。任务列表一目了然。

### 任务完成 = 目标达成吗？

不。所有任务都标记 completed 后，Agent 还需要回到原始目标做一次验证。这正是下一节的内容。


## 验证：做完不等于做对

任务全部 completed 不代表工作结束。Agent 在最终确认前需要跑一轮验证，确保"做了该做的事"和"做对了"是两回事。

### 三层验证

**第一层：自动化验证。** 运行测试、类型检查、lint——用代码本身验证代码。这是最快的反馈回路，能抓住大部分低级错误。

**第二层：功能性验证。** 启动应用，实际操作一下。测试通过不代表功能正确——可能测试本身有 bug，或者需求理解有偏差。实际操作能抓住测试覆盖不到的问题。

**第三层：目标对照。** 回到用户最初的请求，逐条核对：

```text
用户原始请求："升级 React 18，确保所有页面正常工作"

核对清单：
☐ React 版本已升级到 18.x？
☐ 被废弃的 API 已全部替换？
☐ 依赖库已更新到兼容版本？
☐ 所有页面在浏览器中正常运行？
☐ 测试全部通过？
```

### 修复小循环

验证不通过时，Agent 不是从头开始，而是**重新打开相关任务**，标记回 `in_progress`，针对性修复：

```text
执行 → 验证 → 发现问题 → 修复 → 再验证 → 通过
  │                                              │
  └──────────────────────────────────────────────┘
```

这是一个小循环嵌在大循环里。每个问题对应一个任务的重新激活，修复完成后再次验证。大循环保证方向不偏，小循环保证质量过关。


## 实战模式：长任务的几种典型打法

面对不同类型的长任务，Agent 有不同的执行模式。下面四种是最常见的：

| 模式 | 适用场景 | 关键特征 |
|------|---------|---------|
| **线性推进** | 步骤有严格先后顺序 | 任务 A → B → C，依赖链清晰。每个任务 blockedBy 前一个，像流水线一样推进 |
| **并行拆解** | 独立子任务可同时推进 | 多个子代理各自领取任务，互不阻塞。比如同时重构三个不相关的模块 |
| **探索-计划-执行** | 需求模糊，需要先调研 | Plan Mode 调研 → 出计划 → 人类确认 → 执行。最安全的复杂任务处理模式 |
| **迭代增量** | 大功能分批交付 | 每批做一小部分，验证后再做下一批。每批都是一个完整的"计划-执行-验证"循环 |

这四种模式可以组合使用。比如一个大型功能迁移：

```text
第一阶段：探索-计划-执行
  → Plan Mode 调研现有架构，制定迁移方案，人类确认

第二阶段：迭代增量 + 线性推进
  → 每次迁移一个模块（增量），每个模块内按依赖顺序（线性）

第三阶段：并行拆解
  → 独立模块可以并行迁移，多个子代理同时工作

每阶段结束：验证
  → 跑测试、手动操作、目标对照
```

计划与任务系统不是"只有复杂任务才需要"。哪怕只是改一个功能点，"先列计划 → 创建任务 → 执行 → 验证"这套流程也能大幅降低遗漏和方向错误的概率。它让 Agent 的工作从"凭记忆做到哪算哪"变成"按蓝图施工，每步有据可查"。
