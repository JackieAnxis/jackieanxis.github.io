# 记忆系统：Agent 的经验本

如果说 Agent Loop 是 Agent 的心跳，工具系统是它的双手，技能系统是一本训练手册，计划与任务系统是行动蓝图，Subagent 是 Agent 的多线程工作模式——那记忆系统就是 Agent 的**经验本**。

心跳让 Agent 持续思考，双手让它能操作代码，手册教它领域知识，蓝图帮它规划步骤，多线程让它分身并行——但没有记忆，每一次新的会话都是一张白纸。

Agent 不记得上次会话里你说过"这个项目用 bun 不用 npm"，不记得你纠正过"不要用 mock，我们要测真实数据库"，也不记得项目正处于合并冻结期。它每次都要从头开始。

记忆系统解决这个问题。它让 Agent 能够跨会话积累知识、自我修正、携带经验——它不再每次从零开始，而是带着"经验本"里的积累进入每一次新的对话。

## Agent 为什么需要记忆

想象你去同一个诊所看两次病。没有病历系统时，第二次去医生完全不认识你，你得把所有症状、过敏史、之前的检查结果再说一遍。有了病历系统，医生翻开病历："上次开的药效果怎么样？"——对话直接从上次停下来的地方继续。

Claude Code 没有记忆时就是这样。每次启动，它的状态完全来自 CLAUDE.md 和项目文件。项目文件里有代码、有依赖、有架构，但没有：

- 你上次说过的偏好："解释代码时用运维的视角，别用前端那套"
- 团队昨天的决策："这个 PR 合并后合并冻结三天"
- 历史决策的原因："不用 mock 是因为上季度吃过亏"
- 外部系统的位置："Linear 上的 INGEST 项目追踪流水线 bug"

CLAUDE.md 能存一部分项目约定，但它是**静态**的——开发者预先写好，启动后不会变。记忆是**动态**的——会话中自动积累、持续演进、自我修正。

**CLAUDE.md vs 记忆的核心区别：**

| 维度 | CLAUDE.md | 记忆 |
|------|-----------|------|
| 写入时机 | 开发者预先编写 | 会话中自动积累 |
| 更新频率 | 手动修改 | 自动更新、后台整理 |
| 内容类型 | 编码规范、架构约定 | 用户偏好、历史决策、项目动态 |
| 可见性 | 所有会话一致 | 按类型区分私有/团队 |
| 生命周期 | 随项目文件存在 | 可衰败、可整理、可删除 |

没有记忆系统时，Agent 每次启动都是一张白纸——你说一次它记一次，但下次会话就忘了。项目知识全靠 CLAUDE.md 维护，Agent 从犯过的错误和收到的反馈中什么也学不到。

有了记忆系统，你说一次，Agent 就能记住。项目经验跨会话携带，Agent 自动积累知识——它有了"经验"。

## 四种记忆类型

Claude Code 的记忆分为四种类型，每种有不同的作用范围和生命周期。

### 用户记忆（user）

关于你本人的信息：你的角色、技术背景、工作偏好、知识盲区。

**何时记录：** 你介绍自己时（"我是运维出身，不太懂 React"）、表达偏好时（"回复尽量简短"）、提到技术栈时（"我主要写 Go"）。

**作用域：** 始终私有，只影响 Claude Code 和你交互时的行为。

比如你说"我是运维出身，不太懂 React"，Claude Code 会保存一条用户记忆。之后解释前端概念时，它会自动用运维视角来类比，而不是假设你有前端经验。

### 反馈记忆（feedback）

你给过的工作方式指导——不仅是"不要这样做"的纠正，也包括"就是这样，保持"的确认。

**何时记录：** 你纠正 Agent 的行为（"不要 mock 数据库"），或确认某种做法正确（"对，这种 PR 合并方式是对的"）。

**作用域：** 默认私有，当指导明确是项目级约定时存为团队记忆。

反馈记忆有一个核心设计理念：**记录失败和成功同样重要。** 只记纠正，你会避免过去的错误，但会逐渐偏离已经验证过的正确做法。

反馈记忆的正文遵循特定结构：

```markdown
集成测试必须用真实数据库，不使用 mock。
**Why:** 上个季度 mock 和生产差异导致线上迁移失败
**How to apply:** 编写集成测试时不要使用数据库 mock
```

**Why:** 行记录原因——用户给出这条规则的理由，通常是一次历史事件或强烈偏好。**How to apply:** 行记录应用方式——这条记忆如何影响后续行为。知道*为什么*让你判断边界情况，而不是盲目跟从规则。

### 项目记忆（project）

关于项目当前正在进行的工作、决策和约束。不是代码本身的内容，而是围绕项目工作的元信息：谁在做什么、为什么做、什么时候要。

**何时记录：** 你交代任务时（"这周要把 React 升级到 19"）、解释决策原因时（"不拆 PR 是因为改动太小不值得"）、提到时间约束时（"合并冻结到周四"）。

**作用域：** 可以是私有或团队级，但强烈偏向团队级——项目动态对所有人都有用。

```markdown
2026-03-05 起非关键合并冻结，移动端团队在 cut release 分支。
**Why:** 移动端团队正在发布版本，避免合入不稳定代码
**How to apply:** 安排合并时标记非关键 PR 为冻结状态
```

项目记忆有一个特点：**会自然衰败。** 合并冻结结束了、任务完成了、决策过时了——这些记忆仍然存在，但日期让 Claude Code 能判断它们是否还有效。

### 参考记忆（reference）

外部系统的位置和用途：哪个 Linear 项目追踪什么类型的 bug、哪个 Grafana 看板是 oncall 在看的、哪个 Slack 频道讨论什么事。

**何时记录：** 你提到外部资源及其用途时。

**作用域：** 通常是团队级——外部系统的位置对所有人都有用。

```markdown
Grafana 看板 grafana.internal/d/api-latency 是 oncall 监控面板。
**Why:** 修改请求路径代码时需要检查这个看板的延迟指标
**How to apply:** 编辑 request-path 相关代码前查看该看板
```

### 什么不该记

记忆系统的设计不只是决定"该记什么"，同样重要的是决定"什么不该记"。以下内容**不应该**存为记忆：

- **代码模式、架构约定、文件路径、项目结构**——这些可以从当前项目状态直接读取
- **git 历史、最近的改动、谁改了什么**——`git log` 和 `git blame` 是权威的
- **调试方案或修复方案**——修复已经在代码里了，commit message 有上下文
- **CLAUDE.md 里已经覆盖的内容**——不要重复
- **临时的任务细节**——在途工作、临时状态、当前对话上下文——这些会快速过时

判断标准很简单：**这条信息在未来没有代码和 git 的情况下还有用吗？** 如果答案是否定的，就不该存为记忆。

## 记忆的存储：文件与索引

记忆不是存在数据库里的结构化记录，也不是漂浮在上下文里的临时数据。Claude Code 的记忆以**文件**的形式永久存储在磁盘上——每个记忆是一个独立的 Markdown 文件，由 MEMORY.md 作为索引。

### 目录结构

```
~/.claude/projects/{项目标识}/memory/
├── MEMORY.md              ← 索引文件
├── user_role.md           ← 具体记忆文件
├── feedback_testing.md
├── project_freeze.md
└── reference_linear.md
```

项目标识是 git 仓库路径经过哈希处理生成的简短字符串，保证同一项目始终指向同一个目录。

### 单个记忆文件格式

每个记忆文件使用 YAML frontmatter + Markdown 正文的格式：

```markdown
---
name: testing-preference
description: 集成测试必须用真实数据库
type: feedback
---

集成测试必须用真实数据库，不使用 mock。
**Why:** 上个季度 mock 和生产差异导致线上迁移失败
**How to apply:** 编写集成测试时不要使用数据库 mock
```

frontmatter 中的三个字段各有用途：

| 字段 | 作用 |
|------|------|
| `name` | 简短的 kebab-case 标识符，用于去重和内部引用 |
| `description` | 一行摘要，是记忆**被检索时的主要匹配目标** |
| `type` | 记忆类型，决定可见性和默认作用域 |

对于反馈和项目记忆，正文中的 `**Why:**` 和 `**How to apply:**` 不是装饰，而是结构化的——系统在检索和使用记忆时会依赖这些信息。

### MEMORY.md：索引文件

MEMORY.md 是一个纯索引文件，在会话启动时被完整加载到系统提示中。它有严格的限制：最多 200 行、25KB。

格式是一行一个条目：

```markdown
- [集成测试不用 mock](feedback_testing.md) — 集成测试必须用真实数据库
- [合并冻结到周四](project_freeze.md) — 2026-03-05 起非关键合并冻结
- [Grafana oncall 看板](reference_linear.md) — grafana.internal/d/api-latency
```

MEMORY.md 是索引，不是内容。每行约 150 字符，包含文件名和一行钩子。Claude Code 通过它快速了解有哪些记忆存在，而无需逐个读取文件。

### 目录里的其他结构

除了标准的记忆文件，memory 目录还可能包含：

- **每日日志**（Assistant 模式）：`logs/YYYY/MM/YYYY-MM-DD.md`——Agent 在每天结束时追加会话摘要到日期命名的日志文件，每晚的 `/dream` 技能将这些日志提炼为主题记忆文件
- **团队记忆**（TEAMMEM 启用时）：`<memory>/team/MEMORY.md` 及团队级 `.md` 文件——与私有记忆结构相同，但作用域为整个团队
- **Agent 记忆**（Subagent 场景）：`~/.claude/agent-memory/{agentType}/`——子 Agent 的独立记忆空间，没有 MEMORY.md 索引步骤，直接通过类型隔离

## 记忆的生命周期

记忆不是"加载一次就完事"。它经历四个阶段：创建、读取、更新与删除、后台整理。

```
创建 ──→ 读取 ──→ 更新/删除 ──→ AutoDream（后台整理）
  │        │         │              │
对话结束   每轮开始   用户指令        定期触发
自动触发   异步预取   或模型判断     合并·删除·重组
```

### 创建：自动提取为主

记忆有四种创建途径，但最主要的是**自动提取**。

**自动提取（主要途径）。** 在每个对话回合结束时——模型给出最终响应且没有工具调用——系统检查是否满足提取条件，然后在后台启动一个受限的子 Agent 来检查对话内容并创建或更新记忆文件。

这个子 Agent 是受限运行的，不是完整的 Claude Code 实例。它拥有：
- Read/Grep/Glob：无限制读取
- Bash：仅限只读命令（ls、find、grep、cat、stat、wc、head、tail）
- Edit/Write：仅限记忆目录内的路径
- 禁止：MCP 工具、Agent 工具、非只读 Bash、其他写入操作

这种限制保证了提取过程的安全性——子 Agent 只能读取对话和现有记忆，只能写入记忆目录，无法修改项目代码或执行危险命令。

**用户明确指令。** 当用户说"记住这个"时，系统会指示模型立即保存——不等回合结束，直接写入记忆文件。

**/memory 命令。** 打开文件选择器，让用户在编辑器中直接编辑记忆文件。

**/remember 命令。** 触发记忆审查技能——检查所有自动记忆，提议升级到 CLAUDE.md 的条目，检测重复、过时、冲突的记忆。

### 读取：每轮按需检索

每轮对话开始时，系统执行记忆检索流程：

1. **扫描**：递归扫描记忆目录下所有 `.md` 文件（排除 MEMORY.md），解析每个文件前 30 行的 frontmatter，按修改时间倒序排列，上限 200 个文件
2. **格式化**：将扫描结果格式化为清单：`- [type] 文件名 (ISO 时间戳): description`
3. **选择**：调用小模型（Sonnet），传入当前对话的用户消息和记忆清单，让它选出最相关的 5 条
4. **读取**：读取被选中的记忆文件内容（有行数/字节数限制，超长会被截断并提示使用 FileRead 查看完整内容）
5. **注入**：将记忆内容作为 `<system-reminder>` 标签附件注入上下文

整个检索过程是**异步预取**——它在主模型流式输出和工具执行的同时运行，不会阻塞主循环。

被注入的记忆还附带新鲜度标签：

| 记忆年龄 | 显示 |
|---------|------|
| 当天创建 | 无警告 |
| 昨天创建 | `Memory (saved yesterday)` |
| 2 天前 | `Memory (saved 2 days ago)` |
| 超过 1 天 | 附加失活警告 |

失活警告的内容是：

> 这条记忆已保存 N 天。记忆是时间点的观察，不是实时状态——关于代码行为或文件位置的声明可能已过时。在断言为事实前请验证当前代码。

这是记忆系统的一个关键设计：**记忆是快照，不是实时数据。** 一条三个月前的项目记忆可能完全失效，失活标签提醒模型注意这一点。

### 更新与删除

更新记忆时，系统提示 Claude Code 先检查是否有可更新的现有记忆，而不是创建重复条目。修改正文内容、更新 frontmatter 中的 description，或者在不再准确时删除整条记忆。

当用户说"忘记 X"时，Claude Code 找到对应的记忆文件，删除文件本身，并从 MEMORY.md 中移除对应的索引条目。

### AutoDream：后台整理

人类在睡眠时，大脑会整理白天的记忆——合并重复的、删除无用的、加强重要的。Claude Code 有一个类似的功能，叫做 **AutoDream**。

AutoDream 是后台进程，定期整理记忆目录。它触发需要满足所有条件：

| 条件 | 默认值 | 说明 |
|------|--------|------|
| 特性开关 | 启用 | 可通过配置关闭 |
| 时间间隔 | 24 小时 | 距上次整理至少 24 小时 |
| 会话数量 | 5 次 | 上次整理后至少 5 次新会话 |
| 扫描间隔 | 10 分钟 | 两次会话扫描之间的最小间隔 |
| 文件锁 | 单进程 | PID 锁文件防止并发整理 |

整理过程在受限子 Agent 中运行（与自动提取相同的权限限制），经历四个阶段：

1. **Orient**：读取 MEMORY.md 和现有记忆，了解当前状态
2. **Gather**：扫描自上次整理以来的新会话记录
3. **Consolidate**：合并重复记忆、重组主题分类、更新索引
4. **Prune**：删除过时、冲突、不再相关的记忆

整理完成后，Claude Code 通知用户："改善了 N 条记忆"。如果失败，会回滚锁文件的 mtime，让时间门控再次触发。

AutoDream 也可以通过 `/dream` 命令手动触发。

### /memory 与 /remember

除了自动机制，Claude Code 提供两个手动记忆命令：

- **/memory**：打开文件选择器，直接在编辑器中编辑记忆文件。适合想手动维护记忆的场景。

- **/remember**：触发记忆审查技能。它会检查所有自动记忆，提议哪些应该升级到 CLAUDE.md（项目级的持久约定）、检测重复记忆、标记过时条目、发现冲突的记忆。

## 记忆与 Agent Loop 的集成

记忆系统不是独立运行的，它紧密集成在 Agent Loop 的三个时间点上。

```
启动时                    对话进行中                  对话结束后
┌──────────────┐          ┌───────────────────┐       ┌──────────────────┐
│ 加载 MEMORY.md│          │ 每轮检索相关记忆   │       │ 自动提取新记忆   │
│ 注入系统提示  │  ──→    │ 失活检查 + 附件注入│  ──→  │ AutoDream 整理   │
│（只发生一次） │          │（不阻塞主循环）   │       │（异步、受限沙箱） │
└──────────────┘          └───────────────────┘       └──────────────────┘
```

### 启动时：注入系统提示

Claude Code 启动时，`loadMemoryPrompt()` 函数构建记忆系统提示并注入：

1. 计算并注入记忆目录路径
2. 注入四种记忆类型的定义、作用域、示例
3. 注入"什么不该记"的反面清单
4. 注入"如何保存记忆"的两步操作指南（写文件 → 更新 MEMORY.md）
5. 加载 MEMORY.md 内容（如果存在）

系统提示注入后会被缓存——只有记忆目录内容变化时才重新计算，不是每次对话都重建。

此外，系统提示中还包含"基于记忆推荐前验证"的指导：如果记忆命名了某个函数或文件，那是一个*书写时存在的*声明，可能在之后被重命名、删除或从未合并。在推荐前先验证。

### 对话进行中：异步预取

每轮对话开始时，记忆检索作为异步预取运行：

```
提取最后一轮真实用户消息
         │
         ▼
    扫描记忆目录
         │
         ▼
    格式化记忆清单
    ┌─────────────────────────────────────┐
    │ - [feedback] feedback_testing.md    │
    │   (2026-05-27T10:30:00Z): ...       │
    │ - [project] project_freeze.md       │
    │   (2026-03-05T09:00:00Z): ...       │
    └─────────────────────────────────────┘
         │
         ▼
    Sonnet 选择最相关的 5 条
         │
         ▼
    读取选中文件 → 附加 freshness 标签
         │
         ▼
    作为 relevant_memories 附件注入
    包裹在 <system-reminder> 标签中
```

关键设计：这个过程**不阻塞主循环**。它在主模型流式输出和工具执行的同时运行——模型不需要等记忆检索完成就开始思考和行动。检索结果作为附件在下一轮可用。

系统还能检测"自动管理的记忆文件"——当 Claude Code 读取或修改记忆目录内的文件时，系统会将其识别为记忆操作，用于折叠/徽章逻辑和 shell 命令目标检测。

### 对话结束后：自动提取

当模型给出最终响应且没有工具调用时，`handleStopHooks` 触发两个异步操作：

```
回合结束
    │
    ├──→ executeExtractMemories()
    │    检查提取条件 → 受限子 Agent → 写入记忆文件
    │    完成后通知："Memory updated in ..."
    │
    └──→ executeAutoDream()
         检查所有门控 → 如果满足则整理
         失败时回滚锁 mtime，下次重试
```

两个操作都是 fire-and-forget——它们异步运行，不阻塞对话的结束。提取完成后如果保存了记忆，系统会追加一条消息显示更新的文件路径。

### 完整示例：一次记忆的完整旅程

让我们追踪一条记忆从创建到使用的完整链路。

**第一回合：创建记忆**

你说：

> 记住，我们项目的集成测试必须用真实数据库，不要用 mock。

Claude Code 分析这句话，识别为反馈类型。它写入文件：

```
~/.claude/projects/{hash}/memory/feedback_testing.md
```

内容为：

```markdown
---
name: testing-preference
description: 集成测试必须用真实数据库
type: feedback
---

集成测试必须用真实数据库，不使用 mock。
**Why:** 用户明确要求，之前 mock 导致过问题
**How to apply:** 编写集成测试时不要使用数据库 mock
```

更新 MEMORY.md：

```markdown
- [集成测试不用 mock](feedback_testing.md) — 集成测试必须用真实数据库
```

会话结束时，自动提取在沙箱中运行，分析对话内容后可能进一步补充这条记忆的细节。

通知显示：`Memory updated in ~/.claude/projects/.../memory/feedback_testing.md`

**第二回合：记忆被检索**

新的会话，你问：

> 帮我给新的 API 端点写测试

Claude Code 启动时加载 MEMORY.md，看到有一条反馈记忆。

你提出问题后，记忆检索流程运行：扫描 → 格式化 → Sonnet 选择 → 读取 → 注入。

检索系统把这条记忆渲染为附件，注入 Claude Code 的上下文：

```
<system-reminder>
Memory: ~/.claude/projects/.../memory/feedback_testing.md:

集成测试必须用真实数据库，不使用 mock。
**Why:** 用户明确要求，之前 mock 导致过问题
**How to apply:** 编写集成测试时不要使用数据库 mock
</system-reminder>
```

Claude Code 看到这条记忆，在写测试时自动避开 mock 方案，直接使用真实数据库。

这就是记忆系统的完整工作流：你说一次，它记住了，下次自动用上。

## 如何写好一本记忆手册

记忆系统的效果很大程度上取决于记忆的质量。以下是写好记忆的核心原则。

### 先检查再创建

系统提示明确要求："不要写重复的记忆。先检查是否有可更新的现有记忆。"

在保存新记忆前，Claude Code 会扫描已有的记忆文件，判断是否有一条描述相同主题的记忆可以更新，而不是创建一条新的。

### 命名清晰

`name` 字段使用简短的 kebab-case 标识符：

```yaml
name: testing-preference    # ✓ 清晰
name: tp                    # ✗ 无法理解
name: testingPreference     # ✗ 不用驼峰
```

这个名字用于 `[[name]]` 语法关联记忆，以及内部引用和去重。

### 描述决定检索时机

`description` 是记忆被检索时的主要匹配目标。写描述时想一个问题：**未来 Claude Code 看到什么上下文时，需要想起这条记忆？**

```yaml
description: 集成测试必须用真实数据库     # ✓ 具体的行为规则
description: 关于测试的一些偏好           # ✗ 过于模糊
```

模糊的描述在检索时无法被 Sonnet 准确匹配，记忆就会沉睡在目录里，永远不会被唤醒。

### 记录 WHY

对于反馈记忆和项目记忆，`**Why:**` 行是必须的。

知道*为什么*让你判断边界情况，而不是盲目跟从规则。

```markdown
合并时保持单个 PR 包含所有相关改动。
**Why:** 历史记录的完整性——拆分后无法追踪某个功能的完整变更
**How to apply:** 实现功能时把所有相关文件放在一个 PR 中
```

没有 Why 行，这条记忆在遇到边界情况时（"这个重构算相关改动吗？"）就无法提供判断依据。

### 记录 HOW TO APPLY

`**How to apply:**` 行定义这条记忆如何影响后续行为。它是从"知道"到"做到"的桥梁。

```markdown
**How to apply:** 编写集成测试时不要使用数据库 mock
```

这比"记住测试要用真实数据库"更具可操作性——它直接告诉 Claude Code 在什么场景下做什么（或不做什么）。

### 关联相关记忆

在记忆正文中使用 `[[name]]` 语法链接到相关记忆：

```markdown
合并策略参考 [[single-pr-per-feature]]。
```

`[[name]]` 即使当前不匹配任何现有记忆也没关系——它标记了一个值得未来补充的关联。

### MEMORY.md 保持精简

MEMORY.md 有 200 行 / 25KB 的限制。每行约 150 字符，包含文件名和一行钩子。

- 按主题组织，不是按时间
- 更新或删除过时或错误的记忆
- 如果记忆与当前信息冲突，信任现在观察到的——更新或删除过时的记忆

## 记忆与 CLAUDE.md 的边界

记忆不该存什么——这个清单和"该存什么"一样重要。但还有一个更深层的问题：**什么时候该用 CLAUDE.md，什么时候该用记忆？**

| 放在 CLAUDE.md | 放在记忆 |
|---------------|----------|
| 项目级约定（编码规范、架构决策） | 用户偏好和风格 |
| 命名约定、工具链配置 | 跨会话上下文（"上次的讨论"） |
| 很少改变的规则 | 历史决策原因（"为什么不用 mock"） |
| 对所有会话一致的约定 | 外部系统位置（Linear、Grafana） |

一个简单的判断标准：**这条规则对整个项目都适用，且很少改变吗？** 如果是，放在 CLAUDE.md 里。如果是动态的、会话间变化的、关于人或决策历史的，放在记忆里。

CLAUDE.md 是指令，记忆是经验。指令告诉你必须怎么做，经验告诉你过去发生了什么。
