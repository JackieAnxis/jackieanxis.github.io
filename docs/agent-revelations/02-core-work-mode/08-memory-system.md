# 记忆系统：Agent 的经验本

如果说 Agent Loop 是心跳，工具是双手，技能是手册，蓝图是规划，Subagent 是分工——那记忆系统就是 Agent 的**经验本**。

没有记忆，每次新会话都是一张白纸。Agent 不记得你说过的偏好、团队的决策、项目的约束。记忆系统让 Agent 跨会话积累知识、自我修正、携带经验。

## Agent 为什么需要记忆

没有病历系统时，第二次看病要把症状、过敏史、检查结果再说一遍。Claude Code 没有记忆时也是这样——每次启动，状态完全来自 CLAUDE.md 和项目文件，缺少：

- 你说过的偏好和背景
- 团队近期的决策和约束
- 历史决策的原因
- 外部系统的位置

CLAUDE.md 能存约定，但它是**静态**的——预先写好，启动后不变。记忆是**动态**的——会话中自动积累、持续演进。

| 维度 | CLAUDE.md | 记忆 |
|------|-----------|------|
| 写入时机 | 开发者预先编写 | 会话中自动积累 |
| 更新频率 | 手动修改 | 自动更新、后台整理 |
| 内容类型 | 编码规范、架构约定 | 用户偏好、历史决策、项目动态 |
| 可见性 | 所有会话一致 | 按类型区分私有/团队 |
| 生命周期 | 随项目文件存在 | 可衰败、可整理、可删除 |

CLAUDE.md 是指令，记忆是经验。

## 四种记忆类型

### 用户记忆（user）

关于你的角色、技术背景、工作偏好。**始终私有**。

你说"我是运维出身，不太懂 React"，后续解释前端概念时会自动用运维视角类比。

### 反馈记忆（feedback）

你给过的工作方式指导——纠正和确认都记录。**默认私有，项目级约定存为团队记忆。**

核心理念：**记录失败和成功同样重要。** 只记纠正会避免错误，但会逐渐偏离已验证的正确做法。

反馈记忆正文遵循特定结构：

```markdown
集成测试必须用真实数据库，不使用 mock。
**Why:** 上个季度 mock 和生产差异导致线上迁移失败
**How to apply:** 编写集成测试时不要使用数据库 mock
```

**Why:** 记录原因。**How to apply:** 记录应用方式。知道*为什么*才能判断边界情况，而不是盲目跟从规则。

### 项目记忆（project）

项目当前正在进行的工作、决策和约束。**偏团队级。**

```markdown
2026-03-05 起非关键合并冻结，移动端团队在 cut release 分支。
**Why:** 移动端团队正在发布版本，避免合入不稳定代码
**How to apply:** 安排合并时标记非关键 PR 为冻结状态
```

项目记忆**会自然衰败**——合并冻结结束、任务完成、决策过时后，日期让 Claude Code 判断是否还有效。

### 参考记忆（reference）

外部系统的位置和用途。**通常团队级。**

```markdown
Grafana 看板 grafana.internal/d/api-latency 是 oncall 监控面板。
**Why:** 修改请求路径代码时需要检查这个看板的延迟指标
**How to apply:** 编辑 request-path 相关代码前查看该看板
```

### 什么不该记

- **代码模式、架构、文件路径、项目结构**——可从当前项目状态直接读取
- **git 历史、最近改动**——`git log` / `git blame` 是权威的
- **调试方案**——修复已在代码中，commit message 有上下文
- **CLAUDE.md 已覆盖的内容**——不重复
- **临时任务细节**——在途工作、临时状态会快速过时

判断标准：**这条信息在未来没有代码和 git 的情况下还有用吗？** 没有，就不该记。

## 记忆的存储：文件与索引

记忆以**文件**形式持久存储在磁盘上——每个记忆是一个独立的 Markdown 文件，由 MEMORY.md 作为索引。

### 目录结构

```
~/.claude/projects/{项目标识}/memory/
├── MEMORY.md              ← 索引文件
├── user_role.md           ← 具体记忆文件
├── feedback_testing.md
├── project_freeze.md
└── reference_linear.md
```

项目标识是 git 仓库路径的哈希，保证同一项目始终指向同一目录。

### 单个记忆文件格式

```markdown
---
name: testing-preference
description: 集成测试必须用真实数据库
type: feedback
---

集成测试必须用真实数据库，不使用 mock。
**Why:** 上个季度 mock 和生产差异导致线上迁移失败
**How to apply:** 编写集成测试时不要使用数据库 mock
```

frontmatter 三个字段各有用途：

| 字段 | 作用 |
|------|------|
| `name` | kebab-case 标识符，用于去重和 `[[name]]` 内部引用 |
| `description` | 一行摘要，是记忆**被检索时的主要匹配目标** |
| `type` | 记忆类型，决定可见性和默认作用域 |

`**Why:**` 和 `**How to apply:**` 不是装饰，系统在检索和使用时依赖这些结构化信息。

### MEMORY.md：索引文件

纯索引文件，会话启动时完整加载到系统提示中。限制：最多 200 行、25KB。

```markdown
- [集成测试不用 mock](feedback_testing.md) — 集成测试必须用真实数据库
- [合并冻结到周四](project_freeze.md) — 2026-03-05 起非关键合并冻结
- [Grafana oncall 看板](reference_linear.md) — grafana.internal/d/api-latency
```

每行约 150 字符，是索引而非内容。

### 其他结构

- **每日日志**（Assistant 模式）：`logs/YYYY/MM/YYYY-MM-DD.md`——每天追加会话摘要，`/dream` 技能提炼为主题记忆
- **团队记忆**（TEAMMEM 启用时）：`<memory>/team/` 目录——与私有记忆结构相同，作用域为团队
- **Agent 记忆**（Subagent 场景）：`~/.claude/agent-memory/{agentType}/`——子 Agent 独立记忆空间，无 MEMORY.md 索引

## 记忆的生命周期

记忆经历四个阶段：创建、读取、更新与删除、后台整理。

```
创建 ──→ 读取 ──→ 更新/删除 ──→ AutoDream（后台整理）
  │        │         │              │
对话结束   每轮开始   用户指令        定期触发
自动触发   异步预取   或模型判断     合并·删除·重组
```

### 创建：自动提取为主

**自动提取（主要途径）。** 对话回合结束时（模型给出最终响应且无工具调用），后台启动受限子 Agent 检查对话内容并写入记忆。受限子 Agent 拥有：
- Read/Grep/Glob：无限制读取
- Bash：仅限只读命令（ls、find、grep、cat、stat、wc、head、tail）
- Edit/Write：仅限记忆目录内路径
- 禁止：MCP、Agent、非只读 Bash

**用户明确指令。** 说"记住这个"时不等回合结束，立即保存。

**/memory 命令。** 打开文件选择器，直接在编辑器中编辑记忆文件。

**/remember 命令。** 触发记忆审查技能——提议升级到 CLAUDE.md 的条目，检测重复、过时、冲突的记忆。

### 读取：每轮按需检索

1. **扫描**：递归扫描所有 `.md` 文件，解析前 30 行 frontmatter，按修改时间倒序，上限 200 个
2. **格式化**：`- [type] 文件名 (ISO 时间戳): description`
3. **选择**：Sonnet 模型选出最相关的 5 条
4. **读取**：有行数/字节数限制，超长截断
5. **注入**：作为 `<system-reminder>` 附件注入上下文

整个过程**异步预取**，不阻塞主循环。

记忆附带新鲜度标签：

| 记忆年龄 | 显示 |
|---------|------|
| 当天 | 无警告 |
| 昨天 | `Memory (saved yesterday)` |
| 2 天前 | `Memory (saved 2 days ago)` |
| 超过 1 天 | 附加失活警告 |

失活警告：

> 这条记忆已保存 N 天。记忆是时间点的观察，不是实时状态——关于代码行为或文件位置的声明可能已过时。在断言为事实前请验证当前代码。

**记忆是快照，不是实时数据。**

### 更新与删除

更新前先检查是否有可更新的现有记忆，不创建重复条目。用户说"忘记 X"时删除文件和索引条目。

### AutoDream：后台整理

类比人类睡眠时整理记忆。触发需要满足所有条件：

| 条件 | 默认值 |
|------|--------|
| 特性开关 | 启用 |
| 时间间隔 | 24 小时 |
| 会话数量 | 5 次 |
| 扫描间隔 | 10 分钟 |
| 文件锁 | 单进程 |

四阶段：Orient（了解现状）→ Gather（扫描新会话）→ Consolidate（合并重组）→ Prune（删除过时）。完成后通知"改善了 N 条记忆"。也可手动 `/dream` 触发。

## 记忆与 Agent Loop 的集成

```
启动时                    对话进行中                  对话结束后
┌──────────────┐          ┌───────────────────┐       ┌──────────────────┐
│ 加载 MEMORY.md│          │ 每轮检索相关记忆   │       │ 自动提取新记忆   │
│ 注入系统提示  │  ──→    │ 失活检查 + 附件注入│  ──→  │ AutoDream 整理   │
│（只发生一次） │          │（不阻塞主循环）   │       │（异步、受限沙箱） │
└──────────────┘          └───────────────────┘       └──────────────────┘
```

### 启动时：注入系统提示

`loadMemoryPrompt()` 构建并注入：记忆目录路径、四种记忆类型定义、反面清单、保存指南、MEMORY.md 内容。结果被缓存——仅目录内容变化时重建。

系统提示包含"基于记忆推荐前验证"：记忆命名了某函数或文件，是*书写时存在的*声明，推荐前先验证。

### 对话进行中：异步预取

```
提取用户消息 → 扫描记忆目录 → 格式化清单 → Sonnet 选择 5 条 → 读取并附加 freshness → 作为 <system-reminder> 注入
```

不阻塞主循环。系统同时检测"自动管理的记忆文件"，用于折叠/徽章逻辑。

### 对话结束后：自动提取

`handleStopHooks` 触发两个异步操作：

```
executeExtractMemories()  → 受限子 Agent → 写入记忆文件 → 通知路径
executeAutoDream()        → 检查门控 → 满足则整理 → 失败回滚锁 mtime
```

均为 fire-and-forget，不阻塞对话结束。

### 完整示例：一次记忆的完整旅程

**第一回合：创建**

你说"记住，集成测试必须用真实数据库"。Claude Code 写入 `feedback_testing.md`，更新 MEMORY.md。通知：`Memory updated in .../memory/feedback_testing.md`。

**第二回合：使用**

新会话，你说"帮我给新 API 端点写测试"。Claude Code 启动加载 MEMORY.md，检索流程运行，记忆作为附件注入：

```
<system-reminder>
Memory: .../memory/feedback_testing.md:

集成测试必须用真实数据库，不使用 mock。
**Why:** 用户明确要求，之前 mock 导致过问题
**How to apply:** 编写集成测试时不要使用数据库 mock
</system-reminder>
```

Claude Code 自动避开 mock 方案。你说一次，它记住了，下次自动用上。

## 如何写好一本记忆手册

### 先检查再创建

保存新记忆前先扫描已有文件，判断是否可更新而非新建。

### 命名清晰

```yaml
name: testing-preference    # ✓
name: tp                    # ✗
name: testingPreference     # ✗
```

`name` 用于 `[[name]]` 关联记忆和去重。

### 描述决定检索时机

`description` 是检索时的主要匹配目标。写描述时想：**未来 Claude Code 看到什么上下文时需要想起这条记忆？**

```yaml
description: 集成测试必须用真实数据库     # ✓
description: 关于测试的一些偏好           # ✗
```

模糊描述导致记忆沉睡。

### 记录 WHY 和 HOW TO APPLY

反馈和项目记忆必须包含这两行。WHY 提供判断依据，HOW TO APPLY 定义行动指南。

```markdown
合并时保持单个 PR 包含所有相关改动。
**Why:** 历史记录完整性——拆分后无法追踪完整变更
**How to apply:** 实现功能时把所有相关文件放在一个 PR 中
```

没有 Why 行，遇到边界情况时无法判断。

### 关联相关记忆

```markdown
合并策略参考 [[single-pr-per-feature]]。
```

即使当前无匹配也没关系——标记了未来值得补充的关联。

### MEMORY.md 保持精简

200 行 / 25KB 限制。按主题组织，更新或删除过时条目。与当前信息冲突时，信任现在观察到的。

## 记忆与 CLAUDE.md 的边界

| 放在 CLAUDE.md | 放在记忆 |
|---------------|----------|
| 项目级约定（编码规范、架构决策） | 用户偏好和风格 |
| 命名约定、工具链配置 | 跨会话上下文 |
| 很少改变的规则 | 历史决策原因 |
| 对所有会话一致的约定 | 外部系统位置 |

判断标准：**这条规则对整个项目都适用且很少改变吗？** 是 → CLAUDE.md。动态的、会话间变化的、关于人或决策历史的 → 记忆。
