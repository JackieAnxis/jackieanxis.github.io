# AutoDream：Agent 的睡眠记忆整理

人类睡眠时，大脑会逐渐切断外界感知，盘点海马体中残留的短期记忆，然后将其提炼、抽象，转化为大脑皮层的结构化长期记忆，并且在此过程中主动清除无关紧要的细节（如路人的长相），防止大脑信息过载。

AutoDream 就是 Agent 的这个"睡眠整理"过程。

[记忆系统](./09-memory-system.md)介绍了即时记忆提取——每轮对话结束后，fork 子 Agent 在后台自动审查对话，提取值得记住的内容到结构化文件。那是"随手记笔记"。AutoDream 则是更深层的整合：积累够了再批量处理，像人类睡眠一样整理记忆。

## 从即时提取到批量整合

即时提取（extractMemories，上一章的内容）和 AutoDream 是记忆系统的两层，互补协作：

| | 即时提取 | AutoDream |
|---|---|---|
| 人类类比 | 白天随手记笔记 | 睡觉时整理笔记本 |
| 触发频率 | 每轮对话结束后 | 每 24 小时 & 5 个会话 |
| 处理范围 | 当前对话最近的消息 | 多个会话的历史记录 |
| 目标 | 提取新记忆 | 整合、去重、修剪已有记忆 |
| 自动程度 | 完全自动 | 完全自动 |

两者的协作流很清晰：

```text
每次对话结束
    ↓
extractMemories → 提取新记忆片段 → 写入主题文件 + MEMORY.md
    ↓
（积累 24 小时 & 5 个会话后）
    ↓
AutoDream → 回顾所有记忆 + 会话记录
    ↓
合并重复 / 修正过时 / 删除矛盾 / 压缩索引
    ↓
MEMORY.md 和主题文件焕然一新
```

AutoDream 的触发点在每轮 AI 回复完成后的 stop hook 阶段。系统检查是否满足条件，满足就启动一个 fork 子 Agent 来执行整合——fire-and-forget（阅后即焚），不阻塞主会话。

## 五重门控

AutoDream 不是满足一个条件就触发——它有五重门控，按检查开销从低到高逐级过滤：

```text
① 功能开关
   │  isAutoDreamEnabled() → settings.json
   │  isGateOpen() → 排除 autoMemory 未启用
   ↓
② 时间门控（一次 stat）
   │  距上次整合 ≥ 24 小时
   │  读取 .consolidate-lock 的修改时间
   ↓
③ 扫描节流（时间戳比较）
   │  距上次扫描 ≥ 10 分钟
   │  防止"时间门控通过但会话门控未通过"时频繁扫描目录
   ↓
④ 会话门控（目录扫描）
   │  自上次整合后至少 5 个新会话（全新会话 / 整合之后又发生对话的旧会话）
   │  排除当前会话
   ↓
⑤ 锁门控（stat + read + write + re-read）
   │  没有其他进程正在整合
   │  检查 .consolidate-lock 的 PID 是否存活
   ↓
全部通过 → 启动 fork 子 Agent 执行整合
```


## 四阶段整合流程

五重门控全部通过后，系统启动一个 fork 子 Agent 来执行整合。子 Agent 收到的提示词定义了四个阶段的工作流程：

```text
① Orient（定向）
   │  读取记忆目录结构
   │  读取 MEMORY.md 索引
   │  浏览已有的主题文件
   │  → "我现在已经知道什么？"
   ↓
② Gather（收集）
   │  扫描每日日志（logs/YYYY/MM/YYYY-MM-DD.md）
   │  查看已有记忆中与代码库现状矛盾的事实
   │  在会话记录中窄范围搜索
   │  → "最近发生了什么新事情？"
   ↓
③ Consolidate（整合）
   │  将新信号合并到已有主题文件
   │  转换相对日期为绝对日期（"昨天" → "2026-06-04"）
   │  删除被推翻的旧事实
   │  → "更新我的知识体系"
   ↓
④ Prune（修剪）
   │  更新 MEMORY.md 索引
   │  保持在行数和大小限制内
   │  → "确保索引干净可用"
```

四个阶段的逻辑很直觉：先了解现状，再收集新信息，然后整合新旧，最后精简索引。

收集阶段的三个信息源按优先级排列：**每日日志最高**（这是最可靠的追加流），其次是已有记忆中的"漂移"事实（与代码现状矛盾的旧条目），最后才是会话记录的窄范围搜索——提示词特别强调"不要穷尽读取转录文件，只查找你已经怀疑重要的内容"。

整合阶段的核心是**合并而非创建**：新信号应该融入已有的主题文件，而不是创建近似重复的新文件。同时，相对日期（"昨天"、"上周"）必须转换为绝对日期，确保记忆在时间推移后仍然可解释。

修剪阶段对 MEMORY.md 有明确的约束：行数限制、大小限制（约 25KB）、每条索引不超过约 150 个字符。超过 200 字符的索引行会被精简——内容移入主题文件，索引只保留一行摘要。

## 执行与安全

AutoDream 的 fork 子 Agent 与 extractMemories 共享同一套权限函数，受到严格的工具限制：

**文件操作**：
- Read / Grep / Glob：无限制——整合需要读取任意项目文件来验证记忆是否过时
- Edit / Write：仅限记忆目录内——子 Agent 只能修改记忆文件，不能碰项目代码

**Bash 命令**：
- 允许：`ls`、`find`、`grep`、`cat`、`stat`、`wc`、`head`、`tail`——整合需要扫描目录和搜索内容
- 拒绝：所有写入、重定向、修改状态的命令——子 Agent 不应改变项目状态

**其他**：
- MCP / Agent / 工具调用：全部拒绝——子 Agent 专注于记忆整合，不需要其他能力

这个权限设计体现了最小权限原则：子 Agent 拥有"读取一切、只写记忆"的能力——刚好够完成整合工作，不多不少。

## 锁机制

整合过程使用文件锁 `.consolidate-lock` 来保证互斥。这个锁文件有两个用途：记录上次整合时间（用于时间门控判断），以及防止多个 Agent 实例同时整合。

锁文件的设计：

```text
文件内容 = 持有者的进程 ID（PID）
文件修改时间 = 上次整合完成时间（mtime）
```

获取锁的流程：

```text
① 并行读取：stat() 获取 mtime + readFile() 获取 PID
   ↓
② 检查是否过期：mtime 在 1 小时内？
   │  → 在内且 PID 存活 → 锁被占用，放弃
   │  → PID 已死或超出 1 小时 → 可以抢占
   ↓
③ 写入当前 PID
   ↓
④ 回读验证：读回 PID 是否等于自己？
   │  → 是 → 成功获取锁
   │  → 否 → 有竞争，放弃
```

整合失败时，系统会回滚锁文件的修改时间到获取前的值——这样下一轮时间门控不受影响，可以正常重新触发。

## API 层面的 Dreams

除了客户端的 AutoDream，Anthropic 还在 Managed Agents API 层面提供了 Dreams 功能。这是一个异步任务，接受记忆存储（memory store）和最多 100 个会话作为输入，产出一个全新的记忆存储作为输出。

与 AutoDream 的自动触发不同，API Dreams 需要显式创建——适合需要精细控制整合过程的场景，比如指定重点关注哪些类型的会话、通过 `instructions` 字段引导整合方向。输入记忆存储不会被修改，输出是独立的新存储，可以审查后再决定是否采用。

这个 API 尚在 research preview 阶段。它和客户端的 AutoDream 解决的是同一类问题（记忆的定期深度整合），但面向不同的使用场景：AutoDream 是"全自动的后台管家"，API Dreams 是"可编程的整合管道"。
