# 上下文：Agent 的记忆与视野

> 太长不看:
>
> **上下文管理的核心是"缓存稳定性"**——静态/动态分离、Delta 模式、附件增量都为了让 prompt cache 命中率最大化。
>
> API 请求按 tools → system → messages 顺序组装，工具定义跨会话完全不变所以前置于最前，最大化缓存前缀匹配。
>
> 动态内容（Agent 列表/延迟工具列表/记忆）走 Delta 模式——差集计算或路径去重，动态变化如果改静态定义会让前缀不再匹配，整个请求缓存全部失效。Delta 把失效范围从全请求收缩为末尾新增的几条消息。
>
> **缓存稳定性是一切设计的前提。**

每次与 Claude Code 对话，表面是一问一答。但背后，每次 API 调用都在向大模型发送一个庞大的**上下文**——不止你的提问，还包含系统规则、对话历史、工具结果、环境信息、文件内容、记忆片段等。

上下文是 Agent 的"记忆与视野"：它决定了 Agent 此刻能看到什么、知道什么、能做什么。

## 上下文全景：一次 API 调用发送了什么

先建立全局视角。每次 API 请求（以 Anthropic Messages 格式为例）的上下文由三大块组成：

```
┌────────────────────────────────────────────────────┐
│                     API 请求                       │
├────────────────────────────────────────────────────┤
│  system                                            │
│  ├─ 静态区块（全局缓存）                           │
│  │  ├─ 身份与安全                                  │
│  │  ├─ 任务执行原则                                │
│  │  ├─ 工具使用指导                                │
│  │  └─ 语调与风格                                  │
│  └─ 动态区块（会话缓存 + 按需刷新）                │
│     ├─ 环境信息（cwd, git, OS, model）             │
│     ├─ 语言偏好（language, outputStyle）           │
│     ├─ 会话特定指导（工具、技能、MCP 指令）        │
│     └─ 自动记忆（记忆机制、预算、清理提醒）        │
├────────────────────────────────────────────────────┤
│  messages                                          │
│  ├─ [0] <available-deferred-tools>（延迟工具列表） │
│  ├─ [1] <system-reminder> CLAUDE.md + 记忆 + 日期  │
│  ├─ [2] user: "帮我修复这个 bug"                   │
│  ├─ [3] assistant: 文本回复 + tool_use block       │
│  ├─ [4] user: tool_result（工具执行结果）          │
│  ├─ [5] assistant: 文本回复 + tool_use block       │
│  ├─ ...                                            │
│  └─ [n] attachment: 动态注入的附件                 │
├────────────────────────────────────────────────────┤
│  tools                                             │
│  ├─ BashTool: name, description, input_schema      │
│  ├─ FileReadTool: name, description, ...           │
│  └─ ...（所有可用工具的定义）                      │
└────────────────────────────────────────────────────┘
```

三大块各司其职：

| 块 | 作用 | 体积特征 |
|----|------|----------|
| system | 定义 Agent 是谁、怎么做事 | 相对固定，几 KB 到十几 KB |
| messages | 对话历史和动态注入内容 | 持续增长，是上下文的主体 |
| tools | 声明可用的工具列表 | 固定，几 KB 到十几 KB |

上图是逻辑结构，而非 API 请求中的字段顺序。API 内部的实际处理顺序为：

```
tools → system → messages
```

具体而言，API 将工具定义和格式化说明拼接为一段文本，**前置**于 system 提示词，大致结构如下：

```
在此环境中你可以使用一组工具。以下是使用说明...
[工具定义的 JSON Schema]
[你的系统提示词]
[工具配置]
```

这样排序的目标是**最大化缓存命中率**：工具定义跨会话完全不变，system 在会话内相对稳定，messages 持续变化。最稳定的内容置于最前，提示缓存的前缀匹配窗口尽可能大。

下面逐一展开。

## 工具定义：能力的声明

每次 API 请求还包含一个 `tools` 参数——所有可用工具的名称、描述和参数 Schema。

这看似只是技术细节，但对上下文有两重影响：

**占据 token 预算**。每个工具的定义都需要 token。Claude Code 有数十个工具，所有定义合起来可达十几 KB。部分工具采用**延迟加载**（defer_loading）策略——标记为"首次使用时再加载完整 Schema"，减少初始上下文中的 token 消耗。

**影响模型行为**。工具定义不仅是"能不能做"的开关，更是"会不会做"的线索。模型看到 `FileReadTool` 的描述，就知道先读文件再改代码；看到 `AskUserQuestion` 的存在，就知道遇到歧义时可以反问。工具列表定义了 Agent 的行为能力边界。

## 系统提示词：Agent 的世界观

大语言模型每次调用都是**无状态的**，系统提示词在每次调用时定义 Agent "是谁"、"怎么做事"、"用什么工具"、"怎么说话"——是整个行为的底层蓝图（你可能见过类似"你是一名精通xxxx的"的系统提示词示例）。

**系统提示词的质量直接决定 Agent 的行为质量**。

> ### 延伸阅读：为什么系统提示词比其他部分更重要？
> *涉及模型训练和底层知识，跳过不影响后续章节*
>
> **原因 1. 指令微调阶段的角色强绑定（SFT & RLHF）**
>
> 模型从基座演进为对话模型，经历了监督微调（SFT）和 RLHF。若模型为迎合 User 而违背 System，将面临极大的损失函数惩罚——即**在权重层面已内化了"System 优先级绝对高于 User"**，这不是提示词技巧，而是训练写入参数的。
>
> **原因 2. 注意力机制的首位优势与"注意力下沉"**
>
> 近年研究发现 LLM 存在"注意力下沉"（Attention Sinks）现象：无论文本多长，模型都会将极大注意力权重分配给序列开头的几个 token。System Prompt 占据"绝对前排"，成为模型生成的**全局锚点**——对话再长，影响也不轻易衰减。
>
> **原因 3. 概率分布的先验边界**
>
> 大模型的本质是根据上下文预测下一个 token 的概率分布。System Prompt 是概率推演的**第一先验条件**，相当于给模型设定了"全局状态"。若 System 规定"你只能输出 JSON"，所有日常词汇的生成概率瞬间压缩，大括号、引号等符号的概率则大幅提升。User Prompt 仅在这个**已被 System 裁剪好的概率空间内**触发具体任务。

### 静态与动态的分离

系统提示词由多个段落拼装而成，分为两大区域，中间有一条明确的**缓存边界**：

| 区域 | 内容性质 | 缓存策略 |
|------|----------|----------|
| 静态区域 | 通用行为准则，对所有用户一致 | 全局缓存，跨会话复用 |
| 动态区域 | 用户/会话/环境特定的信息 | 会话缓存，关键事件按需刷新 |

### 静态区域

静态区域是 Agent 的"出厂设置"——不关心当前项目，只规定 Claude Code 作为编程 Agent 的行为准则：

- **你是谁**：你是帮助用户完成软件工程任务的交互式 Agent，不是闲聊机器人。
- **基础系统规则**：定义了如何处理输出、权限、外部数据、用户 Hook 和长对话——确保行为安全、可控且符合用户预期。
- **怎么做任务**：先读文件再改代码，做最小必要修改，不顺手重构，不假装测试通过。
- **什么事要谨慎**：本地可逆操作可以直接做；删除文件、强推、发 PR、改共享系统这类高风险操作要先确认。
- **怎么用工具**：有专用工具就优先用专用工具，多个独立工具调用可以并行。
- **怎么说话**：简洁、直接，不用 emoji；引用代码时给出路径和行号。

### 动态区域

动态区域描述**本次运行**的环境、用户偏好和可用能力。它不是一整段上下文，而是一组独立片段，每个片段负责一个具体维度：

| 片段名称 | 内容 | 刷新策略 |
|----------|------|----------|
| 环境信息 | 工作目录、是否 Git 仓库、平台、Shell、OS 版本、当前模型名称和 ID、知识截止日期 | 会话缓存 |
| 语言偏好 | 用户设定的语言偏好指令 | 会话缓存 |
| 输出风格 | 输出风格配置（如简洁程度、表格偏好等） | 会话缓存 |
| 会话指导 | 根据当前启用的工具动态生成的提示——如 AskUserQuestion 使用指导、Agent 工具指导、技能调用说明等 | 会话缓存 |
| 记忆系统指令 | 记忆系统的行为指令（如何写入、访问、分类记忆，不含 MEMORY.md 的实际内容） | 会话缓存 |
| 临时文件 | 会话临时文件目录（`/tmp/`）的使用说明（Agent 可写入临时产出） | 会话缓存 |
| MCP 指令 | 已连接 MCP 服务器的使用说明 | **每轮刷新** |
| Token 预算 | Token 预算目标的指导（仅在启用时注入） | 会话缓存 |

这些片段通过**注册系统**管理，每个片段有名称、计算函数和缓存策略标记。默认片段首次计算后存入会话级缓存，后续轮次直接复用，直到 `/clear` 或 `/compact` 清空。标记为"易变"的片段（目前仅 MCP 指令）每轮重新计算。

#### 缓存策略的两层设计

多数动态段落采用**会话级缓存**：首次 API 调用计算，之后复用——操作系统、Shell、主目录、语言偏好通常不会在会话中途变化。

少数信息/场景例外：

- **MCP 指令**：MCP Server 可能中途连接或断开，因此系统会持续检查，变化时更新上下文
- **`/clear` 与 `/compact`**：清空段落缓存，下次重新生成
- **自定义 system prompt**：由 CLI、SDK、自定义 Agent、协调器、主动模式等入口追加或替换
- **systemContext / userContext**：git 状态、CLAUDE.md、当前日期等由独立通道注入

因此，Claude Code 实际采用：**静态前缀全局缓存 + 动态段落会话缓存 + 少数易变段落按需刷新**。

### 一个完整的系统提示词示例

下面给出一份完整的系统提示词示例，*注*：仅做示例，并非 claude code 的原始系统提示词。

整份提示词由两大区域组成，中间以 `__SYSTEM_PROMPT_DYNAMIC_BOUNDARY__` 标记分隔：

**静态区域**（全局缓存，跨会话复用）：

- 基础系统规则：输出格式、权限模式、`<system-reminder>` 标签语义、Hook 反馈、自动压缩
- 任务执行原则：执行软件工程任务、读文件先于改、不创建不必要文件、不预估时间、诊断后切换策略、安全意识、注释规范
- 操作谨慎性：可逆性、影响范围、风险操作清单（破坏性、不可逆、对外可见、上传第三方）
- 工具使用指导：专用工具优先、并行调用、任务管理
- 语调和风格：禁用 emoji、简短精炼、`文件路径:行号` 引用格式
- 输出效率：直奔主题、聚焦决策/里程碑/阻塞

**动态区域**（会话缓存，按需刷新）：

- 环境信息：cwd、git 状态、平台、Shell、OS、模型 ID
- 语言偏好：与用户语言一致
- 输出风格：与全局语调的细化变体
- 会话指导：AskUserQuestion、`!` 前缀、Agent 工具、技能调用
- 记忆系统指令：行为指令（不含 MEMORY.md 内容）
- 临时文件：`/tmp/` 目录使用说明
- MCP 指令：MCP 服务器工具与资源说明（**每轮刷新**）
- Token 预算：仅在用户设置目标时注入

完整原文见 [references：Claude Code 系统提示词参考](../06-references/01-claude-code-prompts.md#完整系统提示词示例)。

### 为什么需要分离？

系统提示词占据大量 token，每次都完整发送浪费带宽和成本。主流模型 API 提供商支持缓存机制：相同输入可复用 KV Cache（模型推理的中间产物），无需从头推理，大幅降低成本（以 deepseek-v4-pro 为例，命中缓存的价格不到普通价格的 1%）。

因此静态区域放最前面：对所有用户相同，放在首位可最大化缓存命中率。

### 不同模式的提示词策略

Claude Code 在不同运行场景下选用不同的提示词组装方式，决定逻辑是一个**优先级链**，从高到低依次匹配，命中即停止：

- **覆盖**：显式传入 `overrideSystemPrompt` 时直接替换整个提示词，跳过所有优先级逻辑。这是**架构预留的逃逸机制**——代码中已定义但无实际调用者，为未来全自定义场景（如无人值守模式）保留入口
- **[协调器](./08-coordinator.md)**：通过 `CLAUDE_CODE_COORDINATOR_MODE` 环境变量激活的独立模式，系统提示词被**完整替换**为协调器专用提示词，工具集缩减为 Agent/SendMessage/TaskStop。注意：这与 [Agent Teams](../04-the-way-to-agi/02-agent-teams.md) 是两套独立机制——Agent Teams 通过 TeamCreate 工具创建，不替换系统提示词
- **Agent 模式**：通过 `--agent <name>` 将任意 Agent 设为主 Agent，其提示词**替换**默认提示词。
    - 例外：**自主模式**下 Agent 提示词**追加**而非替换——自主驱动能力（自主身份 + tick + Sleep 工具）若被替换将丢失。详见[KAIROS:主动模式](../04-the-way-to-agi/01-kairos.md)
- **`--system-prompt`**：用户通过 CLI 参数传入的自定义提示词，直接**替换**默认提示词
- **默认**：以上均不满足时使用标准静态+动态组合，即本文前述的完整结构

无论哪一级命中，`appendSystemPrompt`（程序自动追加的补充指令）都会拼接到最终结果末尾。它与 `--system-prompt` 不同：前者追加，后者替换。

### Subagent 的系统提示词

Subagent 走另一条独立路径——不经过上述优先级链。它的系统提示词只包含 Agent 自己的提示词 + 少量固定附加内容，不使用默认提示词中的任何静态或动态段落，与 Main Thread 使用 `--agent` 后的最终 system 块对比：

| | Main Thread (`--agent`) | Subagent |
|---|---|---|
| Agent 提示词 | 替换默认 | 替换默认 |
| 环境信息（工作目录、平台、Shell、模型名） | **无** | **有**（XML 格式的 `<env>` 块） |
| 行为备注（绝对路径、禁用 emoji 等） | **无** | **有** |
| Git 状态 (`appendSystemContext`) | 有 | 有（但 Explore/Plan 类型会被剥离） |
| CLAUDE.md (`prependUserContext`) | 有 | 有（但 Explore/Plan 类型会被剥离） |
| 自主模式时的提示词追加 | **有** | **无** |
| 优先级链（协调器/覆盖/`--system-prompt`） | 有 | **无** |

关键差异：Main Thread 被 `--agent` 替换后丢失环境信息块，只能从 `<system-reminder>` 中的文件路径和 gitStatus 间接推断工作目录；Subagent 则有独立的 `<env>` 块。

#### Subagent 提示词的完整概览

1. **Agent 定义**——内置/用户定义的 Agent 提示词。

2. **行为备注（Notes）**——4 条行为约束，强制 Subagent 的输出格式统一：
    - 必须使用绝对路径（因为 Subagent 的 Bash 调用之间工作目录会被重置）
    - 回复中只分享文件路径和关键代码片段，不复述仅仅是读过的代码
    - 禁用 emoji
    - 工具调用前不用冒号

3. **技能搜索指导**——实验性质的内容，提示 Subagent 可以通过工具搜索相关技能。

4. **环境信息（`<env>` 块）**——XML 格式的运行时信息：

```xml
<env>
Working directory: /Users/jackie/project
Is directory a git repo: Yes
Platform: darwin
Shell: zsh
OS Version: Darwin 25.3.0
</env>
```

## 消息历史：上下文的主体

系统提示词定义 Agent 的"出厂设置"，但真正让它理解当前任务进展的，是**消息历史**——占据上下文绝大部分 token 预算。

### 延迟工具列表

```
<available-deferred-tools>
mcp__browser_click
mcp__browser_navigate
mcp__browser_snapshot
mcp__github_create_pr
mcp__slack_send_message
</available-deferred-tools>
```

这条消息列出所有**延迟工具**的名称（详见：[工具系统：Agent 的双手](./03-tool-system.md)），不含任何 Schema。模型必须先通过 ToolSearch "发现"该工具再执行调用。

但这条消息位于 `messages[0]`，带来一个严重的缓存问题：MCP 服务器的变化引起的延迟工具列表变化，将导致前缀不再匹配，其后所有消息的缓存全部无法命中。这正是[Delta 模式](#delta-模式当动态内容威胁到缓存稳定性)要解决的核心场景。

### 用户上下文注入

紧接着，系统自动插入一条 `<system-reminder>` 消息（[记忆系统](./10-memory-system.md)已介绍）：

```
<system-reminder>
# claudeMd
[CLAUDE.md 及其引用文件的内容 + 自动记忆]

# currentDate
Today's date is 2026/05/29.
</system-reminder>
```

*旧事重提*：**为什么 CLAUDE.md 不放在系统提示词中？** 核心原因是**权限隔离**——System Prompt 定义不可逾越的安全红线，CLAUDE.md 是用户编写的项目规范；混在一起若遇恶意 CLAUDE.md 可能劫持安全指令，放在 User Message 中则语义明确：System 优先级始终最高。


### 消息角色与流转

每次对话是三种消息角色的循环往复：

```
user: "帮我修复 src/utils.ts 的登录 bug"
    ↓
assistant: "我先看一下这个文件" + [tool_use: FileReadTool{path: "src/utils.ts"}]
    ↓
user: [tool_result: 文件内容...]
    ↓
assistant: "发现问题了，第 42 行有个错误" + [tool_use: FileEditTool{...}]
    ↓
user: [tool_result: 编辑成功]
    ↓
assistant: "修复完成。原因是..."
```

三种消息角色：

| 角色 | 发送方 | 包含内容 |
|------|--------|----------|
| user | 用户/系统 | 用户输入的文本；或工具执行结果（带 `tool_use_id` 标识对应哪个调用） |
| assistant | 模型 | 回复文本（用户看到的文字）；tool_use block（工具调用的声明，包含工具名、参数、调用 ID） |
| attachment | 系统 | 各种动态注入的附件（见下一节） |

**助理回复**是消息历史的核心，包含两种内容：

- **文本内容**：用户可见的回复——解释、分析、总结、提问
- **tool_use block**：不可见的工具调用声明——模型表达"我要用这个工具、传这些参数"，每个 block 有唯一 ID，系统随后将工具执行结果以 user 消息（携带相同 ID）拼回

模型就是这样"边想边做"：看文件内容（tool_result）→ 发现问题 → 调用编辑工具 → 看到结果 → 确认正确 → 给出文字回复。

### 附件注入

每轮工具循环结束后，系统向消息列表注入各种**附件**（attachment），共 40 多种类型，是动态上下文的核心来源。

以下是几类最常出现的附件：

**用户行为触发的附件：**

| 附件类型 | 触发条件 | 注入内容 |
|----------|----------|----------|
| @引用文件 | 用户输入中包含 `@path` | 被引用文件的完整内容（转换为模拟的 FileReadTool 调用和结果） |
| IDE 选中文本 | IDE 连接且用户选中了代码 | 选中区域的文本和位置 |
| IDE 打开的文件 | IDE 连接但无选中内容 | 当前打开的文件路径和内容 |

**模式状态提醒：**

| 附件类型 | 触发条件 | 注入内容 |
|----------|----------|----------|
| 计划模式 | 处于计划模式 | 提醒在当前会话中保持计划模式 |
| 自动模式 | 处于自动模式 | 提醒自主推进任务 |
| 任务提醒 | 距上次操作/提醒超过 10 轮，或后台任务状态变化时 | 当前未完成的任务列表 |

**Agent 列表增量：**

| 附件类型 | 触发条件 | 注入内容 |
|----------|----------|----------|
| Agent 列表增量 | 可用 Agent 列表发生变化 | 新增/移除的 Agent 名称、用途描述和可用工具 |

**技能列表：**

| 附件类型 | 触发条件 | 注入内容 |
|----------|----------|----------|
| 技能列表 | 有新技能可用 | 技能名称、描述和适用场景 |

**预算控制**：技能描述有严格的 token 预算——不超过上下文窗口的 1%（约 8000 字符）。每条技能描述被截断到 250 字符以内。内置技能不受此限制，始终展示完整描述；用户自定义和项目级技能则可能被截断。

**任务状态通知：**

| 附件类型 | 触发条件 | 注入内容 |
|----------|----------|----------|
| 任务状态 | 后台任务状态变化（完成/失败/终止） | 任务 ID、类型、状态和进度摘要 |

**系统监控附件：**

| 附件类型 | 触发条件 | 注入内容 |
|----------|----------|----------|
| Token 用量 | 每轮生成 | 当前已消耗 token 数量 |
| 预算提醒 | 设置了 maxBudgetUsd | 预算使用情况 |
| 已修改文件 | 跟踪的文件有修改 | 变更文件列表 |
| LSP 诊断 | LSP 有诊断结果 | 编译错误和警告 |

### 附件如何注入

Agent Loop 的每一轮只追加消息、不改历史，附件注入同样遵循此规则。但注入时机并非简单的"每轮一次"，而是分**两个窗口**。

**窗口一：用户提交输入时**。即 Agent Loop 的第一轮——用户输入刚刚到达，模型尚未开始推理。此时注入的附件均源自用户行为：`@path` 引用的文件、`@agent` 引用的 Agent、MCP 资源等。模型在首次回复前即拥有这些上下文。

**窗口二：每轮工具执行结束后**。即 Agent Loop 的后续轮次——模型调用工具，系统执行完毕并返回结果。此时注入的附件反映**工具执行的副作用**：已修改文件列表、诊断信息更新、任务状态变化、Token 消耗量等。模型在下一轮推理前即感知到刚才的操作对环境的影响。

**永久保留，不做清理**。附件一旦进入 `messages` 数组即永久驻留，仅在上下文压缩时被摘要化。同一类信息（如 Token 用量）可能反复出现——几乎每轮工具执行后都会注入一次。目的仍然是为了保证前缀不变，复用缓存。

**增量 vs 全量**。附件每轮都会重新计算，但并非每轮都全量发送。实际分为两类：

- **增量附件**：Agent 列表、技能列表、诊断信息、已修改文件等——仅发送相对于上一轮的新增或变化部分。未变化的部分无需重复注入，因为它们已在消息历史中，模型可直接引用
- **全量附件**：Token 用量、任务提醒、模式状态提醒等——每轮发送完整内容。这类信息体量小（几行文本），全量发送成本低，且模型需要最新完整状态而非增量变化

附件在发送给 API 时转换为标准消息角色。转换方式因附件类型而异：
- 文本提醒变为普通 user 消息（用 `<system-reminder>` 标签包裹后放窗口后）；
- `@` 引用的文件则变为一对 `tool_use`（模拟 FileReadTool 调用）+ `tool_result`（文件内容），与模型自行调用 FileReadTool 的效果完全一致。模型无法区分"用户 @引用的文件"和"自己主动读取的文件"。

**与 CLAUDE.md 的注入对比**。CLAUDE.md 的注入本质与附件相同：最终都是 `<system-reminder>` 包裹的 user 消息，带隐藏标记。区别在于注入管道：
- CLAUDE.md 走**固定前置管道**：每轮调用前拼在消息列表最前面，内容从缓存读取（首次调用时加载，`/clear` 或 `/compact` 时清除缓存并重新读取）
- 附件走**动态追加管道**：在两个窗口中根据当前状态实时计算，追加到消息历史末尾


### Delta 模式：当动态内容威胁到缓存稳定性

附件机制还可用于解决另一类问题：本应静态的内容（一些前缀的内容，如系统提示词、记忆、延迟工具列表等）发生变化时，可通过附件声明增量，而非修改静态定义本身。

**场景一：Agent 列表**。Agent 工具作为内置工具，是 `tools` 参数的一部分，会被放在提示词的最前部。但可用 Agent 列表随用户行为动态变化，容易导致前缀不匹配、缓存全部失效。

**场景二：MCP 指令**。MCP 指令位于系统提示词的动态区域，标记为"每轮刷新"。MCP 服务器可能中途连接或断开，如果此时去更新系统提示词，意味着前缀不匹配、缓存失效。

**场景三：延迟工具列表**。延迟工具列表随 MCP 服务器连接状态实时变化。用户中途连接新 MCP 服务器，如果尝试在列表新增一行工具名——前缀从第一条消息就不再匹配，整个请求的缓存全部失效。

**场景四：自动记忆内容**。记忆文件在会话中途可能被后台守护进程更新。若放在前置的 `<system-reminder>` 中，任何变化都会导致 API 请求前缀不匹配、缓存全量失效。

四种场景指向同一种解法——**Delta 模式**：将动态内容从静态定义中剥离，改为通过附件在消息历史中增量注入。静态定义保持不变，缓存稳定命中；动态变化被隔离到末尾的增量附件中，失效范围从整个请求收缩为新增的几条消息。

#### 增量计算机制

**差集法：Agent 列表和延迟工具列表**。系统扫描所以已存在的资源，在首次附件中公告。后续更新时，与当前可用列表求差集——新增项放入 `addedTypes`，移除项放入 `removedTypes`。

**检索 + 路径去重：自动记忆**。自动记忆的机制不同。它不做差集，而是每轮从全部记忆文件中检索与当前查询最相关的 5 条，按**路径**去重：历史消息中已有该路径的记忆则跳过。

两种机制都**依赖消息历史**——历史中的旧 delta 附件本身就是"已发送内容"的记录。压缩时消息历史被清空，差集结果即退化为全量：Delta 虽沿用 delta 格式，实际上等价于完整列表。

这是贯穿整个上下文管理体系的主题：**缓存是珍贵资源，任何动态变化都应被隔离到尽可能小的范围内**。

后续，我们都将以 **Delta 模式**为准，它拥有更高的缓存命中率。
