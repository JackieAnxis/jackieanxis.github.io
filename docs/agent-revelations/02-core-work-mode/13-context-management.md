# 上下文压缩：当窗口不够用时

> 太长不看:
> **压缩的本质是"为继续工作而丢弃过去"**——四层策略从无感到有感逐步升级，核心是保住工作连续性而非"少字"
> 核心内容：每层触发条件和取舍不同——大结果落盘（>50K 字符自动写磁盘+预览）保护 Agent 还没看过的原文；微压缩（60 分钟/180K token 触发旧工具结果清理为占位符）此时 Agent 已消化过原文，节省空间；完整压缩（fork 子 Agent 在独立上下文生成摘要）不污染主模型工作上下文且能利用缓存；反应式压缩是 API 报错时的紧急防线，按 API 轮次分组从最旧开始丢弃。
>
> 时机关键：自然断点做以最小化缓存损失。

上一章我们看到了上下文的全貌：系统提示词、消息历史、工具定义，每轮 API 调用都在重新发送这一切。这带来一个不可避免的问题——**消息历史只增不减**。

每轮对话都在追加内容：用户输入、Agent 回复、工具调用、工具结果……而上下文窗口有硬上限（例如 200K token），没有任何商量余地。当历史膨胀到接近上限时，Agent 要么压缩，要么停止工作。

这不是一个可选的优化，而是 Agent 持续运行的**硬约束**。更要命的是，Agent 越能干，上下文消耗越快——它会读更多文件、跑更多命令、做更多搜索。能力越强，越需要压缩机制来维持持续运行。

## 四层渐进压缩策略

Claude Code 不是等撞到上限才临时处理，而是从一开始就维护一套渐进策略——从最轻量的操作到最重的操作，逐步升级：

```
单个工具输出太大
  │
  ├─ 第 1 层：落盘持久化 → 写磁盘，留预览（静默，每轮都在做）
  │
工具结果累积过多
  │
  ├─ 第 2 层：微压缩 → 删除旧工具结果（静默，每轮都在做）
  │
整体历史逼近窗口上限
  │
  ├─ 第 3 层：完整压缩 → 生成摘要替换历史（有感知，上下文重置）
  │
压缩请求本身也超限
  │
  └─ 第 4 层：反应式压缩 → 紧急裁剪最旧消息（最后防线）
```

四层策略的设计思想是：**尽量在用户无感知的情况下释放空间，只在必要时才执行有代价的操作。**

下面逐层展开。

## 第 1 层：大结果落盘

工具输出（尤其是 shell 命令、文件读取）往往体积大、信息密度低。一份 3000 行的日志，Agent 看过之后需要记住的可能只是"第 142 行有个 ERROR"。与其让它一直占据上下文，不如落盘后只留引用——Agent 真需要回顾全文时，可以随时从磁盘重新读取。

这是最无声的压缩。Agent 每轮执行工具时，系统都在背后检查工具输出的大小。
当工具结果超过阈值（默认约 50K 字符），系统自动将完整内容写入磁盘，只在上下文中保留一个**引用标记**加一小段预览：

```
<persisted-output>
Full output saved to: /tmp/session-abc123/tool-results/def456.txt
Preview:
─────
test 1: PASS
test 2: PASS
test 3: FAIL - expected 200, got 401
...（前 2KB 内容，按行边界截断）
─────
</persisted-output>
```

## 第 2 层：微压缩（旧工具结果移除）

微压缩发生在每轮 API 调用之前，策略极其简单直接：**删除旧的工具结果内容**。

其主要基于时间触发——当距离上一轮助手消息超过 60 分钟时，系统判定之前的工具结果已经"被消化过了"，可以安全清理（保留最近 5 个工具结果不动）。此外还有基于 token 总量的触发机制——当工具结果累积超过约 180,000 token 时触发压缩，目标将工具结果总量降至约 40,000 token。

### 处理逻辑

微压缩不是无差别删除，而是有选择性地处理特定类型的工具结果：

- 文件读取（FileRead）
- Shell 命令执行（Bash）
- 内容搜索（Grep）
- 文件搜索（Glob）
- 网页搜索和抓取（WebSearch、WebFetch）
- 文件编辑和写入（Edit、Write）

这些工具的共同特点是：输出体积大，但一旦被 Agent 在后续回复中引用过，原文就不再需要常驻上下文。
被清理的位置会被替换为一个占位标记（`[Old tool result content cleared]`），让模型知道"这里曾经有个工具结果，但为了节省空间已被移除"。注意此过程是**不可恢复**的——与第 1 层的落盘不同，微压缩不会把原文写入磁盘。

### 为什么微压缩不做落盘

落盘和微压缩的设计定位不同，核心区别在于**时机**：

- **落盘**发生在工具执行完、结果刚进入上下文的那一刻。此时 Agent 还没看过这个结果，原文还有被回头查阅的价值，所以值得保留。
- **微压缩**发生在很久之后（60 分钟后或 token 累积过多时）。此时 Agent 已经看过这些结果，也已经在后续回复中引用、分析、基于它们做了决策。原文的信息已经被"消化"——提取成了 Agent 文本回复中的要点、决策、结论。其次，微压缩触发的工具往往都是文件相关的，一则具有时效性（容易过期），二则本身就可以从磁盘中再次读取，无需落盘。

换句话说：落盘是为**还没看的大块内容**保留查阅能力，微压缩是为**已经消化过的旧内容**腾出空间。前者值得保留，后者不值得——如果也落盘，只会浪费磁盘，而几乎不会被重新读取，或者无需重新读取。


## 第 3 层：完整压缩

当微压缩释放的空间不够，上下文仍然逼近上限时，系统执行完整压缩（compact）。这是四层策略中**最重的操作**，也是用户感知最强的——执行后，对话历史被一份摘要替换。

### 触发时机

以下两种触发时机使用同一套压缩流程：

- **自动触发**：当上下文大小超过 `有效窗口 - 13,000 token` 时自动执行
- **手动触发**：用户输入 `/compact` 命令

### 核心过程

完整压缩不是"删掉一些消息"这么简单。它是一个精心设计的过程：

**1. 生成摘要**

压缩摘要不是由主模型直接在自己的上下文里"一边工作一边总结"。系统会 fork 一个独立的 Agent 来专门执行压缩任务——这个 forked Agent 继承主对话的模型配置，使用相同的模型来生成摘要，但在独立的上下文中工作。这有几重好处：

- 主模型的工作上下文不被压缩过程污染
- forked Agent 可以完整地审阅对话历史来生成高质量摘要
- 主模型不需要在自己的上下文窗口中同时处理压缩和当前任务
- 使用同个模型来压缩可以有效利用上下文缓存，减少 token 消耗

注意：**压缩的核心不是尽量少字，而是用更少的 token 保住继续工作的连续性。**

**2. 摘要保留什么**

一份合格的压缩摘要，至少要保住这些信息：

| 必须保留 | 为什么 |
|----------|--------|
| 当前任务目标 | Agent 需要知道自己在做什么 |
| 已完成的关键动作 | 避免重复工作 |
| 已修改或查看过的文件 | 保持代码修改的一致性 |
| 关键决定与约束 | 防止做出矛盾的选择 |
| 下一步应该做什么 | 维持工作的连续性 |


**3. 摘要丢掉什么**

被丢弃的主要是：

- 完整的工具输出原文（文件内容、命令输出、搜索结果）
- 中间推理过程
- 已不再相关的历史细节

**4. 重新注入关键上下文**

压缩不是只留一份摘要就结束。摘要只保留了"发生了什么"的叙事，但 Agent 要继续工作还需要更多：文件内容、技能定义、计划状态等。因此压缩后，系统通过一套专门的逻辑（不是复用正常的附件注入管道）来恢复必要的上下文。

```
压缩前，每轮 API 调用发送的内容：
┌─────────────────────────────────────────────┐
│ 系统提示词（API system 参数，不受压缩影响） │
│ ---                                         │
│ <system-reminder>                           │
│（CLAUDE.md + 日期，每轮 prepend，缓存命中） │
│ ---                                         │
│ user: "修复登录 bug"                        │
│ assistant: 读文件 + 分析                    │
│ tool_result: auth.ts 全文（3000 token）     │
│ 附件：已修改文件、技能正文、计划状态...     │
│ ...（更多轮次的对话）                       │
└─────────────────────────────────────────────┘

                   ↓ 压缩（清除 CLAUDE.md 缓存）

压缩后，当即构建的 API 调用内容：
┌─────────────────────────────────────────────┐
│ 系统提示词（不变）                          │
│ ---                                         │
│ <system-reminder>                           │
│（缓存已清除，当即从磁盘重新读取最新         │
│ CLAUDE.md + 当前日期）                      │
│                                             │
│ 摘要（user 消息，由独立 Agent 生成）        │
│     "用户要求修复登录 bug 和 token 刷新。   │
│      已修改 auth.ts（修复 token 过期顺序）  │
│      和 tokens.ts（调整刷新逻辑）。         │
│      测试通过。下一步：确认 session 超时    │
│      处理。"                                │
│ ---                                         │
│ compact_boundary 标记                       │
│（system 消息，不发送给 API）                │
│                                             │
│ -- 压缩后专门注入的附件 --                  │
│                                             │
│ 全量重建：延迟工具列表、Agent 列表、        │
│ MCP 指令、计划文件、计划模式状态、          │
│ 后台 Agent 状态、Hook 结果                  │
│                                             │
│ 文件：从 readFileState 恢复最近 5 个文件    │
│   ├─ auth.ts → 完整内容（≤ 5000 token）     │
│   └─ tokens.ts → 路径引用（超限时降级）     │
│     总预算 50,000 token                     │
│                                             │
│ 技能：实际调用过的技能正文                  │
│       （每个 ≤ 5000 token，总量 ≤ 25K）     │
└─────────────────────────────────────────────┘
```

注意压缩带来的一个附带效果：**CLAUDE.md 的缓存被清除**。正常轮次中，用户消息前的 `<system-reminder>` 是直接从缓存中读取，同一轮会话不发生变化。只有压缩发生时，缓存被清除，才会从磁盘读取最新内容。

## 第 4 层：反应式压缩（紧急避险）

这是最后的防线。当完整压缩的请求本身也因为上下文太长而失败（API 返回 "prompt too long" 错误）时，系统进入紧急模式。

### 处理逻辑

反应式压缩的策略很直接：**从最旧的消息开始，按 API 轮次分组删除**。

1. 将消息按 API 轮次分组（一轮 = 一次模型调用 + 工具结果）
2. 从最旧的组开始丢弃
3. 丢弃后重新尝试压缩
4. 最多重试 3 次，每次丢弃更多消息

这个过程就像飞机抛掉不必要的载重来保持飞行——不是优雅的方案，但能防止坠毁。

### 与前三层的关系

反应式压缩理论上不应该被触发。如果前三层工作正常，上下文不会增长到连压缩请求都无法发送的程度。它的存在是为了应对极端情况——比如工具输出突然暴增，或者模型生成了异常长的回复。

## 压缩后的世界

压缩完成后，Agent 看到的上下文发生了根本性变化。理解这个变化对使用者非常重要。

### 什么存活，什么丢失

| 机制 | 压缩后的状态 | 原因 |
|------|-------------|------|
| 系统提示词 | 不受影响 | 不在消息历史中，独立缓存 |
| 项目根 CLAUDE.md | 缓存清除后当即重新注入 | 以 system-reminder 形式 prepend 到消息历史，压缩时清除缓存，当即从磁盘读取最新内容 |
| 已调用的技能正文 | 重新注入（单个 ≤ 5000 token，总量 ≤ 25K） | 由压缩流程专门恢复 |
| 已读取的文件 | **尝试恢复完整内容；过大时降级为路径引用** | 压缩流程专门恢复最近 5 个文件（每个 ≤ 5000 token，总量 ≤ 50K），单个超过 5000 token 降级为引用 |
| 计划文件与状态 | 重新注入 | 由压缩流程专门恢复 |
| 后台 Agent 状态 | 重新注入 | 由压缩流程专门恢复 |
| Agent 列表 | 重新注入 | 完整 Agent 列表 |
| Hook 结果 | 重新注入 | 原样保留，放在附件末尾 |
| MCP 指令 | 重新注入 | 全量重新公告 |
| 路径作用域规则 | **丢失** | 随匹配文件加载，压缩后消失 |
| 子目录 CLAUDE.md | **丢失** | 需要再次读取该目录的文件才恢复 |
| 技能描述列表 | **丢失** | 只保留实际使用过的技能 |
| 对话中的口头指令 | **丢失** | 没有持久化，被摘要替代 |

这张表解释了一个常见困惑：**"我明明在 CLAUDE.md 里写了规则，为什么压缩后 Agent 不遵守了？"**

答案往往是：规则写在子目录的 CLAUDE.md 或带 `paths:` 前缀的规则文件里。这类规则是"按需加载"的——只有读取匹配文件时才进入上下文，压缩时随消息历史一起被摘要掉。如果规则必须跨压缩存活，应该放在项目根目录的 CLAUDE.md 中。

### 缓存代价

压缩还有一个容易被忽略的间接代价：**提示缓存完全失效**。

在 Claude 的 API 中，缓存按前缀匹配工作。压缩改写了整个消息历史，导致前缀完全不同，下一轮 API 调用必须重新处理全部内容——意味着压缩后的第一轮会明显更慢、更贵。

这也是为什么压缩的时机很关键：**在任务间隙做，不要在任务中途做。** 在一个自然断点压缩（比如修完一个 bug 准备开始下一个），缓存损失的影响最小，因为 Agent 即将开始全新的工作，之前的缓存本来也快失效了。

## 压缩与 Agent 主循环

从这一章开始，Agent 的主循环不再只是"收消息 → 调模型 → 跑工具"的简单循环。它还承担了一个持续的责任：**管理上下文预算**。

```
while 任务未完成:
    执行微压缩（清理旧工具结果）
    检查上下文大小
    if 超过自动压缩阈值:
        执行完整压缩
    调用 API
    处理响应
    if 响应是 prompt_too_long 错误:
        执行反应式压缩，重试
```

主循环现在同时维护两件事：**任务推进**和**上下文预算**。两者之间需要平衡——过于激进的压缩会丢失关键信息，过于保守则可能撞到硬上限。

这个设计让压缩对用户尽量透明：前两层（落盘和微压缩）完全无感，第三层（完整压缩）有感知但系统自动处理，只有第四层（反应式压缩）才意味着"出了问题"。

## 延伸：还有什么机制参与上下文管理

压缩是上下文管理最核心的机制，但不是唯一的。还有两个值得注意的实验性机制：

**上下文折叠（Context Collapse）**：普通完整压缩将整个对话历史一次性替换为摘要，而 Collapse 采用**按消息组逐步压缩**的策略——当上下文占用达到约 90% 时触发，将消息按组替换为摘要（具体什么叫消息组、如何摘要，已泄露的代码中的实现尚未定义）。原始消息不会被删除，只是在每次发送给模型前替换成摘要文本。模型看到的是摘要，而非原始历史。这种方式的好处是：如果后续需要恢复，重置 collapse store 即可还原完整历史。目前属于实验功能。

**会话记忆压缩（Session Memory Compact）**：与传统压缩最大的区别是**不调用 API 生成摘要**，而是直接读取已有的 `{projectDir}/{sessionId}/session-memory/summary.md` （在每次发起模型调用的同时，如果判断新增 ≥ 3 次工具调用，或者最后一个 assistant 回合没有工具调用，也即一个自然对话断点，都会 fork 一个 subagent 来生成 `summary.md`）文件内容作为压缩后的上下文。它保留最近的 10K–40K token 和至少 5 条文本消息，删除更旧的内容，用已总结的内容填充压缩边界。因为不需要额外的 API 调用，速度更快，但在上下文连续性方面不如 AI 生成的摘要可靠。同样属于实验功能。

除此之外，以下机制也在从不同角度帮助管理上下文：

- **子代理的独立上下文**：研究任务委托给子代理，文件读取和搜索发生在子代理的独立窗口中，只把摘要返回给主窗口。本质上是"通过隔离来避免膨胀"。
- **记忆系统**：将跨会话仍然重要的信息持久化到磁盘，即使对话被压缩或清空，关键经验和偏好也不会丢失。
- **路径作用域规则**：只在读取匹配文件时才加载规则，避免所有规则都常驻上下文。
- **MCP 工具延迟加载**：工具名称列表在启动时加载，但完整的参数 Schema 在首次使用时才加载。

这些机制与压缩共同构成了 Agent 的上下文管理体系——**压缩解决"当前会话太长怎么办"，其他机制解决"如何从一开始就减少不必要的上下文消耗"**。
