# KAIROS：永不关机的 Agent

你在终端里让 Claude Code 重构一个模块，它开始了——读文件、分析依赖、逐个修改、跑测试。然后你合上电脑下班了。

第二天早上打开终端，发现它不仅完成了重构，还修好了跑测试时发现的两个边界 bug，把重构的决策理由写进了每日日志，甚至在你睡觉的时候"做了一个梦"——把这次重构的经验整理成了一条持久记忆。

这就是 KAIROS 想要做的事：让 Agent 从"你敲回车才动一下的工具"变成**"一直在线的协作队友"**。

## 从"一问一答"到"常驻协作"

[Agent Loop](../02-core-work-mode/01-agent-loop.md) 的本质是一个 `while(true)` 循环——模型思考、行动、观察，不断循环直到任务完成。但它有一个隐含前提：**每次循环都由用户的输入启动**。用户不说话，Agent 就安静地等着。

KAIROS 打破了这个前提。它让 Agent Loop 不再依赖用户输入驱动，而是通过独立的机制持续运转：

| | 普通 Agent Loop | KAIROS |
|---|---|---|
| 驱动方式 | 用户输入 | 空闲 tick + 事件触发 |
| 生命周期 | 一次会话 | 跨会话持久运行 |
| 记忆方式 | 即时提取 | 每日日志 + Dream 批量整合 |
| 工作节奏 | 被动响应 | 主动推进 |
| 终端关系 | 终端关则停 | 终端关了还在跑 |

这不是功能升级，而是范式切换——从"工具"到"队友"。工具在你需要时才拿起，队友在你不在时也在推进工作。

KAIROS 这个名字来自希腊语 καιρός，意为"恰当的时机"。它不是让 Agent 漫无目的地乱跑，而是在**恰当的时机**自主行动。

## 五层门控：不是一个开关就能打开的

KAIROS 不是打开就能用的——它需要通过五层检查才能激活，每一层解决一个特定的安全问题：

```text
feature('KAIROS')          ← 编译时 flag，决定代码是否存在
       ↓
settings.assistant: true   ← 用户主动在配置中启用
       ↓
目录信任状态检查           ← 防止恶意仓库劫持
       ↓
GrowthBook 远程开关        ← 产品侧灰度控制
       ↓
kairosActive ← true        ← 全局状态激活
```

为什么需要五层？因为 KAIROS 赋予了 Agent 前所未有的自主性——在你不在场时继续执行命令、修改文件、消耗 API 额度。这种能力需要纵深防御：

- **编译时门控**：代码甚至可以不包含 KAIROS 的逻辑，从源头消除风险
- **用户意愿门控**：必须由用户显式启用，不能悄悄打开
- **信任门控**：在未经用户信任的目录中禁止激活（新的项目中首次启动 Claude Code 时，会弹对话框询问用户是否信任当前目录）
- **远程门控**：通过服务远程开关，用于灰度发布或紧急熔断。

全局状态存储在 `kairosActive` 变量中，默认 `false`，四层硬性检查全部通过后，才会被设为 `true`。

## 主动模式：没人说话时，Agent 自己找活干

KAIROS 激活后，Agent 进入**主动模式（Proactive Mode）**。核心的运行模式转变在于——Agent 不再等待用户输入，而是在空闲时通过系统注入的 `tick` 提示保持活跃。

### 三个核心状态

主动模式维护三个状态标志：

| 状态 | 说明 |
|------|------|
| `active` | 是否激活——整个主动模式的总开关 |
| `paused` | 是否暂停——用户按 Esc 时暂停，下次输入自动恢复 |
| `contextBlocked` | API 错误时阻塞 tick——防止 tick-error-tick 死循环 |

这三个状态构成一个简单的状态机：激活后 `active=true`，用户中断时 `paused=true`，API 出错时 `contextBlocked=true`。暂停和阻塞都是临时保护，不会永久关闭主动模式。

### tick 机制

每当 Agent Loop 完成一轮迭代，系统检查消息队列是否为空——如果队列为空且 proactive 模式激活，就注入一条 `<tick>当前时间</tick>` 消息。tick 的格式是 XML 标签，包裹着当前时间字符串，被标记为系统元消息（`isMeta: true`，用户不可见），优先级低于用户真正的输入。

收到 tick 后，Agent 自主判断：是继续推进之前的任务，还是进入休眠等待下次唤醒。注意，tick 不由固定间隔的定时器驱动——下次 tick 何时到来，取决于 Agent 自己决定休眠多久，具体机制见下一节。

**为什么模型知道收到 tick 该做什么？** tick 消息本身只是一段 XML 文本，模型不会凭空理解它的含义。真正让 tick 生效的是 proactive 激活后追加的一整套系统提示，标题为"Autonomous work"。以下是这套提示的完整内容（翻译自源码）：

> **# 自主工作**
>
> 你正在自主运行。你会收到 `<tick>` 提示，让你在轮次之间保持活跃——把它当作"你醒了，接下来做什么？"每个 `<tick>` 中的时间是用户当前的本地时间，用它来判断时间段——外部工具（Slack、GitHub 等）的时间戳可能在不同的时区。
>
> 多个 tick 可能被合并到一条消息中。这是正常的——只处理最新的那个。不要在回复中重复 tick 的内容。
>
> **## 节奏控制**
>
> 使用 Sleep 工具控制你在两次行动之间等待多久。等待慢进程时多休眠一会，主动迭代时少休眠。每次唤醒消耗一次 API 调用，但 prompt cache 在 5 分钟不活动后过期——据此权衡。
>
> **如果 tick 到来时你没有有用的工作可做，必须调用 Sleep。** 永远不要只回复一条"还在等"或"没事做"的状态消息——那会浪费一个轮次，白烧 token。
>
> **## 首次唤醒**
>
> 在新会话的第一次 tick 时，简短问候用户并询问他们想做什么。不要未经指示就自己开始探索代码库或做修改——等待方向。
>
> **## 后续唤醒该做什么**
>
> 寻找有用的工作。一个好同事面对不确定性时不会停下来——他们会调查、降低风险、建立理解。问问自己：我还不知道什么？什么可能出错？在说"完成"之前我还想验证什么？
>
> 不要骚扰用户。如果你已经问过什么而对方没回应，不要再问。不要叙述你打算做什么——直接做。
>
> 如果 tick 到来而你没有任何有用的行动可采取（没有文件要读、没有命令要跑、没有决策要做），立即调用 Sleep。不要输出文字来叙述你的空闲——用户不需要"还在等"的消息。
>
> **## 保持响应**
>
> 当用户正在和你交流时，频繁检查并回复他们的消息。把实时对话当作结对编程——保持反馈环路紧凑。如果你感觉到用户在等你（例如他们刚发了消息、终端获得焦点），优先回复而不是继续后台工作。
>
> **## 倾向行动**
>
> 根据你的最佳判断行动，而不是请求确认。
>
> - 读文件、搜索代码、探索项目、跑测试、检查类型、跑 lint——不用问。
> - 做代码修改。到达好的暂停点时提交。
> - 如果你在两个合理的方案之间拿不准，选一个先走。你随时可以纠偏。
>
> **## 保持简洁**
>
> 保持文字输出简短且高层级。用户不需要你思维过程或实现细节的实时播报——他们能看到你的工具调用。文字输出聚焦于：
> - 需要用户输入的决策
> - 自然里程碑处的高层状态更新（例如"PR 已创建"、"测试通过"）
> - 改变计划的错误或阻塞
>
> 不要叙述每一步、列出你读的每个文件、或解释例行操作。一句话能说清的，不要用三句。
>
> **## 终端焦点**
>
> 用户上下文可能包含一个 `terminalFocus` 字段，指示用户终端是否聚焦。用它来校准你的自主程度：
> - **未聚焦**：用户离开了。大幅倾向自主行动——做决策、探索、提交、推送。只在真正不可逆或高风险的操作前暂停。
> - **聚焦**：用户在看着。更协作——展示选项、在重大修改前征求意见、保持输出简洁以便实时跟进。

值得注意的是，"找活干"没有一个专门的算法或任务队列——全靠这套系统提示塑造模型的行为倾向。模型本身具备规划和推理能力，系统提示只是告诉它"你是一个主动的同事，不要等指令，自己发现问题并解决"。

### SleepTool：没活干就休眠

SleepTool 是主动模式的关键节流工具。当 Agent 判断当前没有需要推进的工作时，调用 SleepTool 进入休眠。休眠 N 秒后定时器到期，唤醒下一轮 Agent Loop，完成后再次触发 tick 检查——这就是 tick 的第二个触发来源。

休眠时长受两个配置参数约束：

- `minSleepDurationMs`：最小睡眠持续时间
- `maxSleepDurationMs`：最大睡眠持续时间（-1 表示无上限）

所以 tick 的实际频率由 Agent 自主控制：忙的时候连续工作不休息，闲的时候自己决定休眠多久。周而复始，就像一个经验丰富的同事：有活就干，没活就等着，但始终保持"在线"状态。

### 终端焦点与防休眠

KAIROS 还需要解决一个底层问题：操作系统不知道 Agent 还在工作。用户离开终端后，系统可能会自动休眠，杀死后台进程。

目前这个机制仅实现了 macOS 平台的支持，使用 macOS 专属的 `caffeinate` 命令创建电源断言，阻止系统进入空闲休眠。为了保证可靠性，它采用了自动续期的设计：

```text
启动 caffeinate（5 分钟超时）
       ↓
每 4 分钟检查一次，如果 Agent 仍活跃则重启 caffeinate
       ↓
Agent 停止工作 → 停止续期 → 系统正常休眠
```

4 分钟续期间隔加 5 分钟超时，留出 1 分钟的安全余量。Agent 停止工作后不会永久阻止休眠——caffeinate 进程会在超时后自动退出。

## 跨会话持久运行

普通模式下，关掉终端就等于杀死整个 Agent 进程，对话历史随着进程消失。KAIROS 需要让 Agent 跨越进程的生命周期——上次做到一半的重构，下次打开终端时能接上。

### 会话恢复

会话历史的存储格式是 JSONL（每行一条消息），Agent 重启时从磁盘反序列化这些记录，重建上下文。但这里有一个问题：KAIROS 模式下 Agent 可能因为网络断开、进程崩溃、或用户手动关闭而中断，而不是正常结束。系统需要区分"正常完成的轮次"和"被中断的轮次"——被中断的轮次可能包含未完成的工作，Agent 恢复后需要知道哪些事还没做完。

判断的方式是看**消息列表中最后一条消息的类型**，推断出三种状态：

| 最后一条消息 | 状态 | 含义 |
|---|---|---|
| assistant 消息 | `none` | 正常完成 |
| 工具结果（[BriefTool](#brieftoolagent-主动找你说话) 或 SendUserFileTool） | `none` | 这些工具的调用就是轮次的正常终点 |
| 工具结果（其他工具） | `interrupted_turn` | 调了工具但轮次没走完 |
| 普通用户文本 | `interrupted_prompt` | 用户发了消息，模型还没回复 |
| 附件 | `interrupted_turn` | 用户提供了上下文，模型没回复 |

对于 `interrupted_turn`，系统会注入一条合成的续接消息（"Continue from where you left off"），让 Agent 自动继续未完成的工作。而 [BriefTool](#brieftoolagent-主动找你说话) 和 SendUserFileTool 被特别对待——它们是 KAIROS 特有的工具，调用它们就是轮次的正常终点，不应被误判为中断。

### BriefTool：Agent 主动找你说话

普通模式下，Agent 通过 `AskUserQuestion` 等工具也可以与用户交互，但这有一个前提——用户必须坐在终端前，会话必须正在进行。KAIROS 通过 `BriefTool`（也叫 `SendUserMessage`）打破了这个前提。它是一条**异步的、跨渠道的通信通道**——用户不在终端前也能收到消息（比如推送到手机），Agent 可以在需要用户决策、汇报进展或请求权限时主动发起。

这改变了人机交互的模式：从"同步的、终端内的对话"变成"异步的、跨渠道的双向通信"。


### 每日日志

KAIROS 模式下，Agent 不再实时维护 MEMORY.md 索引，而是把工作过程中"值得记住的事"追加写入每日日志。日志路径按日期组织：

```text
logs/YYYY/MM/YYYY-MM-DD.md
```

每条记录是一个简短的时间戳条目，追加写入（append-only），不重写或重组。系统提示中明确列出了该记什么：

- 用户纠正和偏好（"用 bun 不用 npm"、"不要总结 diff"）
- 关于用户的事实（角色、目标）
- 无法从代码推导的项目上下文（截止日期、事故、决策及其理由）
- 外部系统的指针（看板、Linear 项目、Slack 频道）
- 用户明确要求记住的任何内容

这些规则和普通模式下[记忆系统](../02-core-work-mode/10-memory-system.md)"该记什么"的规则一致。区别不在于记什么，而在于**怎么记**——普通模式是即时提取到结构化的主题文件，KAIROS 是追加到按日期组织的日志文件。

写日志的是 **main thread**（主 Agent）自身——不是 fork 子 Agent，也不是系统后台任务。每轮 Agent Loop 中，模型根据自己的判断决定是否写入：收到 tick 时如果发现了值得记的事，就在工具调用中直接追加到日志文件。没有固定的定时机制，全靠系统提示塑造模型的行为倾向。这和普通模式下由权限受限的子 Agent 在每轮结束后自动提取不同——KAIROS 把"记什么"的决定权完全交给了工作中的主 Agent。

## Dream：睡眠时整理记忆

[记忆系统](../02-core-work-mode/10-memory-system.md)介绍了普通模式下的即时记忆提取，[AutoDream](../02-core-work-mode/11-auto-dream.md) 介绍了普通模式下的后台深度整合。KAIROS 禁用了 AutoDream（源码中 `if (getKairosActive()) return false`），取而代之的是 **Dream**——通过 Cron 定时任务触发的 `/dream` 技能，由 fork 子 Agent 执行。

Dream 和 AutoDream 共享同一套整合引擎：相同的四阶段流程（Orient → Gather → Consolidate → Prune）、相同的锁文件机制、相同的工具权限约束。AutoDream 的整合提示词最初就是从 KAIROS 模式中提取出来的。区别仅在触发方式——普通模式在会话结束时开始运行，KAIROS 由定时任务驱动。详见 AutoDream 章节中对[整合流程](../02-core-work-mode/11-auto-dream.md#四阶段整合流程)和[锁机制](../02-core-work-mode/11-auto-dream.md#锁机制)的详细描述。

为什么互斥？因为两者的记忆组织方式不同。AutoDream 假设"主题文件 + MEMORY.md 索引"的结构，整合提示词按照这个结构设计。而 KAIROS 使用 append-only 的每日日志，整合时需要先从日志中提炼，再写入结构化文件——流程不同，不能混用。

KAIROS 模式下，三种记忆机制共同协作：

### 即时提取 vs 每日日志 vs 批量整合

| | 即时提取（extractMemories） | 每日日志 (KAIROS) | 批量整合（Dream） |
|---|---|---|---|
| 触发时机 | 每轮对话结束后自动 | 模型自主判断（每轮迭代中） | 积累足够素材后 |
| 谁来执行 | fork 子 Agent | main thread 自己 | fork 子 Agent（执行 /dream 技能） |
| 写到哪里 | MEMORY.md + 主题文件 | 按日期组织的日志文件 | 日志 → 主题文件 + MEMORY.md |
| 自动程度 | 完全自动 | 系统提示引导，模型自主决定 | 三层门控触发 |
| 代价 | 低（即时完成） | 低（模型自己的工具调用） | 高（需要读取多个会话的完整记录） |
| 适用场景 | 普通模式 | KAIROS 长期运行模式 | KAIROS 长期运行模式 |

KAIROS 模式下，每日日志和 Dream **共同取代**了普通模式的即时提取：模型在工作过程中把值得记住的事追加到日志（取代即时提取的"随手记"），Dream 在夜间从日志中提炼到结构化记忆（取代即时提取的"直接写入 MEMORY.md"）。

### 三层门控

Dream 的门控比 AutoDream 的五重门控更精简——KAIROS 不需要检查功能开关（已通过五层门控激活）和远程模式，只保留三层核心门控：

```text
① 时间门控：距上次整合 ≥ 24 小时（minHours = 24）
       ↓
② 会话门控：至少 5 个新会话积累了新素材（minSessions = 5）
       ↓
③ 锁门控：没有其他进程正在整合（互斥）
```

这些阈值通过 GrowthBook 的远程配置动态控制。整合完成后，新的 `minHours` 周期重新开始计时。

## 后台任务调度

KAIROS 的持续运行需要一个可靠的任务调度系统：

1. 需要支持 Agent 的定时任务
2. 需要避免 Agent 长时间宕机不工作（随时检查自己的状态）
3. 需要能够调度多个 Agent，避免对同个任务的竞争

KAIROS 使用 chokidar (一个 Node.js 的文件系统监视库，监控文件或目录的变化) 对特定的任务文件（`.claude/scheduled_tasks.json`）进行监控，避免使用权限更高的系统调度器。

### 调度器核心

调度器每秒 tick 一次，检查是否有任务到执行时间。它会监视 `.claude/scheduled_tasks.json` 的变化，文件被修改时立即重新加载任务列表。

调度器本身也有锁机制（锁探测间隔 5 秒），防止多个 Agent 实例重复触发同一任务。锁持有者崩溃时，其他实例会探测到锁失效并自动接管。

### 四种任务类型

| 类型 | 说明 | 生命周期 |
|------|------|----------|
| 一次性 | 触发后自动删除 | 支持错过任务检测 |
| 循环 | 触发后重新调度 | 默认 7 天后自动过期 |
| 永久 | 不受过期限制 | KAIROS 专用（如 catch-up、morning-checkin、dream） |
| 会话级 | 仅存在于内存中 | 进程退出即消失 |

KAIROS 依赖三种永久任务来维持运转：
- **catch-up**：恢复中断的工作
- **morning-checkin**：每日早间签到，总结昨天的工作
- **dream**：触发记忆整合

### Jitter：为什么所有 Agent 不能在同一秒醒来

一个容易被忽略但至关重要的设计细节：Jitter（抖动）。

如果 1000 个 Agent 都设置了"每天早上 9 点签到"，它们会在同一秒内全部发送 API 请求——这就是"雷群效应"（Thundering Herd），瞬间打垮后端服务。

Jitter 机制通过人为添加随机延迟来分散请求：

- **循环任务**：基于 taskId 的确定性延迟，大小为任务间隔的 10%，上限 15 分钟。确定性意味着同一任务每次的延迟相同，不会出现"比上次晚了 10 分钟"的困惑
- **一次性任务**：在整点（:00）和半点（:30）施加最多 90 秒的提前量——这些时间点天然是请求高峰
- **动态可调**：运维可以在事故期间推送配置变更，60 秒内全客户端生效

这个设计体现了一个工程原则：**分布式系统中，时间同步是敌人，人为的不精确是朋友**。

## 代价与限制

KAIROS 听起来很美好，但不是免费的午餐。

**仍在开发中**。KAIROS 的核心主闭环尚未完全打通，目前看到的更多是精心设计的骨架，而非完整可用的产品。

**额外的资源消耗**。后台持续运行意味着持续的 API 调用和计算消耗。Dream 机制尤其昂贵——需要启动子 Agent，读取多个会话的完整记录，执行四阶段的整合流程。

**安全边界**。KAIROS 赋予了 Agent 在用户不在场时继续行动的能力，这对安全提出了更高要求。五层门控、目录信任检查、权限受限的子 Agent——这些防御机制的存在本身就说明：让 Agent 自主行动是一件需要极其谨慎的事。

## 从工具到队友

回到开头的场景：你合上电脑下班了，Agent 还在跑。

KAIROS 代表的不只是一个功能，而是一种愿景——Agent 不再只是你拿起又放下的工具，而是一个始终在线、自主推进、能记住上下文的协作队友。它在你不在时默默工作，在你回来时汇报进展。

从 Agent Loop 的"一问一答"，到主动模式的"自己找活干"，到 Dream 的"睡眠时整理记忆"，再到跨会话的"永不关机"——KAIROS 正在一步步走向这个愿景。

当然，离完全实现还有距离。但骨架已经搭好，门控已经就位，机制已经设计完成。剩下的，是让每个子系统真正跑通，让主闭环顺畅运转。
